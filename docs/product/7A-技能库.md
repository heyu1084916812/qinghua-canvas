## 7A. 页面四：技能库

> **2026-09-27 改口径**：技能库从后台设置的一个分区升为一级页面。
> 原 `/skills` 只有「左列表 + 右编辑」，本次改成**卡片浏览 → 点击卡片编辑**的两层结构，
> 并把功能预设词并入本页。
>
> **2026-10-01 内置技能落地**：随包内置技能来自 `src/assets/builtin-skills/*.md`，
> 启动时同步进只读的 `builtinSkills` 表；用户技能单独存 `skills` 表。已支持复制为我的技能、
> 编辑用户副本、恢复默认，旧版 `presets:skill:*` 会自动迁移。
>
> **2026-09-28 排版口径**：三层各自居中，不贴工作区左边缘。做法是「外层舞台铺满 + 内层内容块居中」：
> 舞台仍是 `width:100%` 并铺满工作区，内容块 `margin-inline:auto` 收窄居中；
> 浏览层最宽 **1120px**，编辑层与功能预设词层最宽 **900px**。窄屏时内容块随可用宽度收缩，
> 不产生横向滚动。卡片内名称与说明必须有 `min-width:0`，长文本只允许在卡片内换行 / 省略，
> 不允许撑破卡片；同一行卡片等高，元信息贴卡片底部。
>
> **2026-10-21 LibTV 技能库改版**：浏览层改为占满右侧工作区的全屏设计，不再收窄到 1120px；
> 一级来源分 `LibTV / 即梦 / 我的`。卡片为三列横图版式，双击打开详情灯箱；
> 编辑表单保留为详情内的次级入口。

> **2026-10-27 LibTV v2 内容分类（对账 #784）**：旧分类 `推荐 / 专业影视 / 商业广告 /
> 短剧漫剧 / 动漫游戏 / 音乐MV / 自媒体创作 / 通用技能 / 发现` 全部退役。
> 新分类按“用户要做什么”划分为 `全部 / 图像创作 / 视频创作 / 人物角色 / 电商品牌 /
> 影视剧情 / 动漫游戏 / 音频音乐 / 文案策划 / 后期工具`。每条目录数据保存唯一 `category`，
> 旧 `tags` 只作原始溯源与搜索，不再决定分类；零条目的分类不显示空标签。

### 7A.2 第二层：详情与编辑

| 区域 | 规则 |
| --- | --- |
| 详情顶部 | 上方是示例图片或视频；预览左上角显示「创作详情」外链（来自 `caseItems[].canvasCaseUrl`），右上角显示媒体类型 |

| 详情操作 | 保留「收藏」「添加 Skill 到 Agent」与关闭；当前只支持单技能，添加到 Agent 时按需落成一条用户技能并写入默认技能。旧口径是「默认技能只影响会话设置、不显示 chip」；对账 #836 将收敛为“正文有 skill chip 才注入”，避免无提示地影响出图 |
| 编辑入口 | 即梦 / 我的技能在详情底部提供「编辑 Skill」；内置技能进入只读编辑态，可复制为我的技能、恢复默认 |
| 功能预设词 | 仍从工具栏进入第二阶段，展示并编辑「优化 / 翻译 / 反推」三条系统指令 |
| 返回 | 从编辑 / 预设词回到浏览层时保留来源、分类与搜索状态 |

### 7A.3 数据规则：内置与用户技能必须分开

| 项 | 口径 |
| --- | --- |
| 内置技能 | 随应用内置；默认只读；后续功能节点可直接依赖其正文 |
| 用户技能 | 用户新建、导入、或从内置复制后产生；可编辑 |
| 复制为我的技能 | 复制当前内置正文到用户技能；之后的修改只影响用户副本 |
| 恢复默认 | 内置技能永远保留默认正文；用户副本的恢复是“重新复制默认正文”，不修改内置记录 |
| 存储 | **不同表**：内置技能与用户技能分表存储，不用同一张表的标记位区分 |
| 导入 / 导出 | 用户技能支持 Markdown；内置技能不写入用户表 |
| LibTV 外部目录 | 只读资源 `public/libtv-skills/catalog.json`；1472 条目录、764 份可执行正文按 UUID 懒加载，不写用户表 |
| LibTV 无正文 | 仍展示简介、示例媒体和画布案例；不能添加到 Agent，卡片与详情都明确标注「暂无正文」 |
| LibTV 收藏 | 收藏是用户与技能的关系，复用 `presets` 的 `skill:favorites`；取消收藏不删除目录内容 |
| 添加到 Agent | 单技能优先：有正文的 LibTV Skill 按需复制为一条用户技能，并写入 `presets` 的 `agent:skill`。旧实现的新会话会自动应用该默认技能；对账 #836 的快速路径要求只有当前正文出现 skill chip 时才注入技能，新会话不得再隐藏应用默认技能 |

> 内置技能正文的唯一来源是 `src/assets/builtin-skills/*.md`。新增技能只加 Markdown，
> 不改数据库迁移；启动同步会幂等更新内置表，并移除已下架的内置项。
>
> **2026-10-01 即梦 Skill 包导入**：上表后 7 条来自用户提供的「即梦 Skill」压缩包，
> 每份只内置主 `SKILL.md` 正文（含 YAML `description: >` 折叠块解析）。
> 正文上限因此从 8000 放宽到 128000 字（上限表同见「功能对账清单 · 技能库」）。
>
> **2026-10-01 第二轮：两个技能升级为「完整版」**。用户随后又给了
> 「即梦好莱坞级镜头设计系统」包，它正是上一批 `创作分镜` / `TVC` 两个技能缺的
> `references/*.md` 来源。**当前运行时只把技能正文当作一份系统指令发送，
> 没有外部文件按需读取机制** —— 所以 references 若不入正文就永远不会被加载。
> 处理方式：把主文档与 references **按顺序合并进同一份正文**，而不是新增近似重复的技能。
> - `创作分镜`：v1.9 主文档 + `cinematography` / `quality-anchors` / `director-styles` /
>   `audio-tags` / `seedance-specs` / `scenarios`，约 3.7 万字（v1.8 单文件版已被取代）。
> - `TVC 商业广告视频创作流程`：官方 v2.0 SOP + 场景配置 YAML + `stage-*.md` 七份 +
>   `prompt-*.md` 九份，约 1.5 万字。
> - `视频反解` 的 `references/*.md` **未随包提供**，仍是纯正文；这是已知留白，不是遗漏。

> **为什么不能同表**：后续功能节点要稳定引用内置技能正文；若内置与用户技能共表，
> 用户编辑或删除会直接影响功能节点依赖的行为。分表后，“系统行为”与“用户内容”互不污染。

### 7A.4 功能预设词迁入技能库

功能预设词的三条系统指令从渠道配置迁到技能库的「功能预设词」分类；
渠道配置页不再展示该分区。

排版与第二层一致：预设词内容块在工作区水平居中（最宽 900px），
每条指令独立成卡片，编辑区与恢复 / 保存操作跟随该卡片，不贴工作区左边缘。

**它解决什么**：提示词节点上的「优化 / 翻译 / 反推」是三个内置动作，各有一段
**系统指令**决定它做什么。此前这三段指令**写死在代码里** —— 用户看得到按钮，
却无法表达「我想让优化多保留一点原话」这类需求。本区把它们变成可编辑。

| 项 | 口径 |
| --- | --- |
| 可改什么 | **只改指令正文**；动作名称（优化 / 翻译 / 反推）与说明不可改 —— 它们描述的是这个动作的身份 |
| 存哪 | `presets` 表一行（`presetText:tools`）；它是用户覆盖，不改内置默认正文 |
| 生效时机 | **点保存即生效**，且执行链路取的是**生效值** —— 只存进库、执行时仍用常量，是「改了没反应」的典型形态，必须有断言拦住 |
| 恢复默认 | 写 `null` **清掉覆盖值**，而不是写回一份默认值副本：于是「改坏后恢复」与「从没改过」在数据上是同一状态 |
| 长度上限 | 2000 字（它是系统指令，占 token；再长就该改用技能） |
| 坏数据 | 库里若出现空白 / 超限值，**读回时丢弃并回落默认** —— 不产出半份状态（一个没有指令的请求比默认行为更糟） |

**与技能的区别（别混）**：预设词 = 改造**内置**的三个动作；技能 = 新增**自己的**动作。
两者现在同在技能库一级页面下用分类区分；在画布上仍是「三个固定按钮」与「技能选择器」。


### 7.5 数据模型（`channels` 表） · ✅ 已实现

| 字段 | 类型 | 状态 | 说明 |
| --- | --- | --- | --- |
| `id` / `name` | string | ✅ | UUID / 平台名称 |
| `baseUrl` | string | ✅ | 请求地址 |
| `credentialRef` | string \| null | ✅ | 凭据引用，指向平台凭据库 |
| `tokenTail` | string \| null | ✅ | 已存令牌的尾 4 位，仅供展示识别（见 §7.3 令牌小节；长度 < 12 时为 null） |
| `protocol` | string | ✅ | 协议 id，指向 `domain/project/protocol.ts` 的协议目录（内置 `BUILTIN_PROTOCOLS` + 用户自建 `customProtocols`）。老渠道沿用 `mock` / `openai-images` / `openai-chat`；新站点用 `openai-compatible` 或站点条目。未登记 id 界面按「未知协议」显示，不猜能力 |
| `imageProtocol` | enum | ⛔ | 生图专用协议（无第二种生图格式可选，暂不落字段，避免空壳） |
| `models` | `Model[]` | ✅ | **已选**模型：画布 / 漫画的模型下拉只读这一份 |
| `modelCache` | `Model[]` | ✅ | 已拉取的**全部**模型缓存：只喂选择面板 |
| `order` | number | ✅ | 左侧列表排序位（拖动 = 整表重编号；同值回落 `createdAt` 倒序） |
| `enabled` | boolean | ✅ | 启停 |
| `lastTestAt` / `lastTestLatency` | number \| null | ✅ | 上次「验证地址」或「验证协议」命中的时间与往返延迟（ms）；二者语义同源，都是「一次成功的往返」 |

**读回补值（只补不删）**

| 情形 | 口径 |
| --- | --- |
| 老数据没有 `models` 键（本字段引入前写下的行） | 读回**回落为全部 `modelCache`**，即沿用旧行为；键一旦存在（哪怕值是 `[]`）就以它为准——用户取消全选也是合法状态，不能被回落覆盖 |
| 老数据没有 `order` | 补 `0`，退化为「按创建时间倒序」，与加排序前完全一致 |
| 老数据没有 `tokenTail` / `lastTest*` | 补 `null` |

新增字段均**不进 Dexie 索引**，故 schema 版本无需变动（`channels: 'id, protocol'` 保持原样）；排序在 `list()` 里做，不在数据库层做。
