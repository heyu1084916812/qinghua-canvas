### 7.2 左侧：渠道列表 · ✅ 已实现

| 规则 | 说明 |
| --- | --- |
| 列表项 | **两块横排**（用户 2026-10-08）：左 = **图标**（固定大小，方块与右侧两排等高）；右 = **两排**（上：自定义名称、下：启用开关）。内距四边同值 8px ⇒ 图标离左边 / 上边 / 下边的留白一致（此前左右 12、上下 8，左边距与上下边距不一致）。超长名称省略号收尾，不换行（换行会把行高与图标方块带跑）。协议短标签自第 21 批起**不在界面上显示**，只作为 `data-channel-proto` 供自动化读取 |
| 排序 | 支持拖动排序 |
| 新增 | 「+ 新增渠道」按钮作为列表最后一项，紧贴**最后一条渠道** |
| 删除 | 紧接「+ 新增渠道」**下方**，同属列表尾部操作组，点击**就地二次确认**后才执行；未选中渠道时禁用 |
| 选中 | 卡片底色 + 细聚焦描边（`--bg-surface` + `--stroke-focus`），与 hover 的 `--bg-hover` 明确区分；**选中在按下那一刻生效**（`pointerdown`，见下） |

**实现说明**

- **新增与删除必须挨着，并跟随最后一条渠道**：两者都是**列表级**操作，放在一起才找得到。删除按钮原先孤零零挂在右栏最底部，既远、又容易被读成「保存类」按钮——用户报的「已保存的渠道怎么无法删除」，根因是**找不到**，不是删不掉（代码路径一直是通的）。后来又发现这一组被列表的 `flex: 1` 钉在左栏最底部，渠道少时与条目之间隔着大片空白，视线要跨越整个列表。现把两者并入列表，作为**最后一个子项**紧随末条渠道（`data-channel-actions`）：渠道少时紧挨列表，渠道多时随列表一起滚到底部，语义仍是列表级操作。
- **删除不可逆 → 就地二次确认**：点一下即把按钮原位换成「删除「渠道 X」？不可撤销 / [确认删除] [取消]」，不弹窗、不跳走，视线不动。切换渠道时残留的确认态会被清掉，避免「删除 A？」跟着光标挂到 B 头上。
- **协议短标签与协议目录同源**：短标签只有一个来源——`domain/project/protocol.ts` 的 `ProtocolDefinition.short`（自建协议也一样）。界面不允许自己拼标签，分两处写迟早会漂。
- **新渠道落在列表末尾**，与按钮位置一致，也不去和用户手工拖出来的顺序抢位置。列表顺序由 `order` 决定（拖动 = 整表重编号），**内存态与落库态必须同一套顺序**：`create` 之后重读整表，不在内存里 unshift 到队首（否则「刷新一下顺序就变了」）。
- **两排的排序**：名称在上、启用开关在下（用户第 21 批把开关从「基本信息」搬进列表项，
  第 22 批又把「N 个模型 / 未选模型」那一行删掉 —— 列表项只剩图标、名称、开关三样，
  模型挑没挑在右侧「模型列表」里看得见）。开关留在**自己那一排**里，与名称同宽对齐。
- **选中走 `pointerdown`，不走 `click`**（用户 2026-10-08：「渠道与渠道之间转换的时候有延迟，
  有时候需要点击两下才能转换」）。根因是**整行就是拖动手柄**（`draggable`）：按下之后指针
  只要移动约 5px，浏览器就进入**拖动判定**，那一下 `click` 根本不派发 —— 实测位移 0–3px 能切换、
  5px 与 8px 一律切不动。挂在按下那一刻即与拖动判定彻底脱钩，顺带把「按下去立刻有反馈」还给用户。
  开关那一排因此必须自己收 `pointerdown`（否则点开关会顺手换选中）。
- **图标列是个方块，尺寸与右侧两排共用一个常量**（`--channel-icon-box`）。这个数被用户改过两轮：
  44 → 56（「上下高度不够，需要放大图标」）→ **44**（同一天又说「太大了，缩小一点」），
  当前是 **44px 方块 + 26px 图标**、行高 **62px**。图标离左边 / 上边 / 下边各
  `1(描边) + 8(内距) + (44 − 26) / 2 = **18px**`，三者仍然相等。
  ⚠️ `align-self: stretch` + `aspect-ratio: 1` 在 flex 项上**不生效**（实测得到竖条而非方块），
  所以要显式给尺寸；「两部分高度一致」由这个共享尺寸保证。改尺寸时**三处一起对齐**
  （方块 / `ChannelIcon` 的 `size` / 内距），否则那条"三边留白相等"立刻被打破。
- **第二排 = 开关 + 模型数**（用户 2026-10-08：「不要有启用的那个文字，替换成显示右侧选择了
  多少个模型的总数即可」）：显示 **`N 个模型` / `未选模型`**（= 该渠道已勾选的模型数，
  也就是右侧「已选模型」的条数）。两件事刻意分开 —— **开关是唯一的控件**，模型数是信息，
  所以它放在收指针的那一层**外面**：点它是**选中这一行**（既不误切开关，也不是死区）。
  开关因此没了可见文字 ⇒ `input` 上补 `aria-label`。文案规则照 `ui-ux-pro-max` 那条
  「计数要说成人话」：**不摆裸数字**（`6 个模型` 而不是 `6`），且不换行（窄了省略号 + `title` 给全量）。
- **左栏整体的尺寸**（同为"缩小一档"）：栏宽 264 → **240px**、内距 20/16 → 16/12、
  名称 15 → **14px**（`--fs-nav`；再小就掉到 12px 那一档）。
- **滚动条贴左栏最右沿、不留白**（用户 2026-10-08：「我想要靠近渠道选择菜单栏的右边，
  不能有留白，叠加在菜单栏的上面」）：滚动容器 `margin-right: -12px`（= 侧栏右内距）+
  等值 `padding-right` ⇒ 滚动条落在左栏边界上、**内容位置不变**；`scrollbar-gutter: stable`
  （出现 / 消失不跳一格）。
   **外观一律沿用全局那套**（`src/ui/base.css`：4px、无箭头、滚动时轨道 `--bg-surface`、
   拇指 `--text-3` 半透明、悬停加深；空闲 1 秒后整体透明）—— 用户 2026-10-08 后续又点明：
   「滚动条这个项目全局统一成右边那个粗细和颜色」⇒ **本地不再覆盖轨道颜色**，
   高特异性全局状态规则负责所有嵌套滚动容器。
  ⚠️ 三个坑都写在代码注释里：**本地再写一份 `::-webkit-scrollbar` 会盖掉全局**（层叠上
  `.list::-webkit-scrollbar` 赢过全局的 `::-webkit-scrollbar`，于是同一页出现两套外观）；
  **只留 `::-webkit-scrollbar` 一套**（再写 `scrollbar-width` / `scrollbar-color` 会被
  Chromium 整片忽略、滑块淡到看不见）；**headless 浏览器不画滚动条** ⇒ 这条只能在真壳里量 / 截图。
- **右栏第一张卡与左栏同一条顶线**（用户 2026-10-08：「图二中第一个框，上面空的，要和左边顶对齐」）：
  `.editor` 的**上内距为 0** —— 左栏那块底色从工作区最上沿就铺满，卡片再留 20px 上内距，
  顶上就会留出一条"空着的白带"。实测 `cardTop == workareaTop`（129 == 129）。
  左右 24px 与底部 20px 不变（卡片仍不贴边）。
- **基本信息卡**（右栏第一张）：标题**不再带小字**（用户 2026-10-08：「第二个框，不需要这个小字」——
  卡片里就一个"名称"输入框，是什么不用再解释一遍）；图标那行拆成
  **当前图标 | 上传按钮 | 支持格式（`PNG / JPG`）** 三块，并给 `.fieldRow` 补 12px 间距
  （此前是 `gap: 0` ⇒ 三块首尾相接，正是用户说的"内容挤压在一起了"；
  末尾那句"自动缩到 128px"是实现细节，用户明确不要，已删）。
- **谁能拖**（用户 2026-10-08 第 2 条：「上面三个渠道是固定不变的，但是新建的渠道是需要可以拖动排序的」）：
  **内置三条不可拖**（`draggable={false}` + `cursor: default` —— 它们本来就拖不动，手型别再骗人），
  **用户渠道可拖**；把用户渠道拖到内置行上是"挪到用户区第一格"的意思，所以内置行**仍然接 drop**。
  整个列表项 `user-select: none`（从名字上起拖不会先划出选区）。
- 按钮文案沿用「+ 新增渠道」（与本节标题、全局用词一致），示意稿里的「新增平台」不再单独保留。
- **开关那一排只占自己的宽，右边不留死区**（用户 2026-10-08 框出那一块：「点击好像不能实现」）：
  它在列布局里默认被 `align-items: stretch` 拉满到右侧栏的宽（**= 该行最长子元素，也就是模型名**），
  而它又 `stopPropagation` 收走指针 ⇒ 开关文字右边那一条**既不是开关、也不归行**，
  点了什么都不发生（名称越长这条越宽：内置 ModelScope 那一行实测 51px）。
  改成 `align-self: flex-start` 之后，那一条回归**行的背景**：点它 = 选中这条渠道；
  点开关本身仍只切开关、不换选中。

**协议从「适配器开关」升格为声明**（用户 2026-09-28「一站一协议」）：一条协议声明它的适配器族（`family`）、可用能力集合（`capabilities`）、版本段（`versionPath`）与默认地址（`defaultBaseUrl`）。渠道因此**只建一条**，同一站的对话模型进提示词节点、生图模型进生成节点，靠模型 `category` 分流，不再需要为同一个中转建两条渠道。协议定义只住在 `domain/project/protocol.ts`（内置目录 `BUILTIN_PROTOCOLS` + 自建合并成 `ProtocolCatalog`），注册表按 `capabilities` 分派适配器。

协议指 API 请求格式，与 HTTP/HTTPS 和模型能力分类无关。

**能力边界（领域层没有的不假装支持）**：`ModelCapability.category` 目前只有 `chat | image | video`，没有音频与 3D。故协议 `capabilities` 也只到这三项；音频 / 3D 站点先记为待支持，等领域层有能力定义再开。自建协议只允许勾选对话 / 生图——视频 / 音频 / 3D 没有对应适配器，允许勾选等于让用户配一条跑不通的渠道。

**状态口径 `ready` / `pending`**：`ready` = 注册表里有适配器、可以真的发请求；`pending` = 只登记「有这么回事」，界面显示「待支持」且不可选。没有官方依据的端点**不写死**——宁可 pending，也不填一个猜出来的路径让用户在「验证失败」里绕圈。

**异步任务族（`async-task`，APIMART）**：与同步 OpenAI 兼容不是同一条链路——提交只回 `task_id`，产物要轮询 `GET {base}/tasks/{task_id}`，终态 `completed` 时从 `result.images[].url[]` / `result.videos[].url[]` 取地址再下载。依据 `docs.apimart.ai` 官方文档。故该族只声明 `image` / `video`，不声明 `chat`。

**RunningHub（`runninghub-api`，同属 `async-task` 族但独立实现）**：取结果是 `POST {host}/openapi/v2/query`（body 给 `taskId`）回 `results[]`，与 APIMART 的 `GET /tasks/{id}` + `result.images[].url` 不通用 ⇒ 在**同一族内按协议分流**（`registry.ts` 里一行 `if`，既有行为零改动）。**标准模型直接用显示名**（全能图片PRO / 可灵 v3.0 Pro…，扣**金额**）、**AI 应用用 `app:` 前缀**（扣 **RH 币**）；验 Key 打 `POST /uc/openapi/accountStatus`。依据是官方 CLI 仓库 `HM-RunningHub/RH_CLI` 的源码，不是猜的。能力声明 **image + video**：模型表里 9 个生图 + 8 个视频，规格与必填默认值都按官方目录逐端点建。

**它的模型清单**（2026-10-08）：官方 CLI 的端点目录里有 356 个端点，界面只给**精挑的 17 个模型**（9 个生图 + 8 个视频），
名称是给人看的（「全能图片PRO」「可灵 v3.0 Pro」…）而不是端点 id。同一个模型有文生 / 图生两个端点，
**节点连了参考图就自动走图生档** —— 用户不必理解 t2i / i2i 这层，也不会出现「模型选好了、图也连了，请求却发错端点」。
端点上的必填参数（官方目录里带默认值的那些）由适配器照官方 CLI 的规则**自动补齐**，所以不会出现「必填缺失」这类看不懂的报错。

**CLI 网关族（`cli-gateway`，即梦 / GPT / Gemini CLI）**：浏览器里跑不了本机命令，也不拿不到 CLI 的登录态，因此这类协议要求用户**先跑一个网关**把 CLI 包成 OpenAI 兼容 HTTP。适配器已实现（按能力分派到既有的 chat / images 适配器），但**当前标 `pending`**：前提不成立时不给可用入口。等有桌面壳或内建本地桥，改 `status` 即可启用，适配器无需重写。

**为什么名字里不写能力**（如「OpenAI 兼容」而不是「OpenAI 兼容（对话 + 生图）」）：带能力后缀会让人以为这条协议**只**做这两件事，进而去找「视频 / 音频 / 3D 协议」。实际上视频走的是同一条 OpenAI 兼容 HTTP（只是端点不同）；音频 / 3D 是 `ModelCapability.category` 没有的定义，故领域层不支持。协议名只描述**形态**，不假装是能力清单。

**旧协议为什么不删**：`openai-images` / `openai-chat` 是老渠道已落库的值，从目录删除会让它们变成「未知协议」、适配器也认不出族（`registry.ts` 的 `LEGACY_FAMILY` 依赖这两个 id）。故保留识别能力，但**新渠道下拉里不再显示**。

**三个动作各问各的问题**（本页最容易混的地方，所以按钮文案与状态行文案都不共用）：

| 动作 | 问的问题 | 产出 |
| --- | --- | --- |
| 验证协议 | 这个地址是不是 OpenAI 兼容 HTTP？是哪个站？ | 命中的协议（或按 host 找回的站点协议）写进「协议」并落库 |
| 验证地址 | 这个地址活着吗、多快？ | 连通结论 + 延迟（`lastTestAt` / `lastTestLatency`） |
| 拉取模型 | 这个地址上有些什么模型？ | 全部模型写进 `modelCache`（见 §7.4） |

**探测只留一条通用模板**：改版前是「逐条协议打一遍、第一个通过即命中」，而 `openai-images` 与 `openai-chat` 都打 `/v1/models`，同一个中继必然被两条同时命中，协议落在哪条全看候选表顺序（即 M6-16）。现在只有 `openai-compatible` 带 `probe: true`，探测问的就只剩「这个地址是不是 OpenAI 兼容 HTTP」，不再冒充「能力归属」。
**离线协议（`mock`）必须被剔除**：它的 `verify` 恒成功，一旦入选候选表，探测在**任何**地址上都会第一个命中它——「自动选中」就变成了假动作。这是「候选表只放会失败的协议」这条不变量的具体形态。

**地址为空时不发请求**：空串会让 URL 退化成**相对当前页**的路径（`/v1/models`），而 dev server / SPA 对任意路径都回 200 的 `index.html`——「验证通过」是纯假象。故 `requiresBaseUrl(protocol)` 为真且地址为空时，验证与探测都直接报「请先填写地址」。

**200 不等于「这里是 OpenAI 兼容接口」**：SPA 兜底页、登录页、网关默认页都会对任意路径回 200。所以适配器要求响应体里**真的有一份模型列表**（`data` 数组）才认成功，否则「验证协议」会在任何地址上都命中第一个候选协议，自动选中同样退化成假动作。

**为什么「生图协议」仍空着**：注册表里只有一种生图格式，摆出来也没有第二个选项可选，用户点它只会**没有任何反应**——正是本页此前被抱怨的那类假完成。控件在该维度真的存在选择余地时再加，本节标记随之更新。

#### 多凭据槽位（2026-10-08，RunningHub 两把钥匙）

有的站点要**两把钥匙** —— RunningHub：「一个是币的，一个是金额的」。实测同一把 Key 打标准模型 API 回 `errorCode 812 企业版余额不足`、打 AI 应用列表成功，证实**币与金额是两本账**。故令牌区按协议声明渲染：

| 规则 | 说明 |
| --- | --- |
| 协议声明槽位 | `ProtocolDefinition.credentials?: {id, label, hint, required}[]`；**没声明就回落成一行**（老渠道零迁移） |

#### 表单态与落库：验证/拉取前先写库（所见即所验）

右侧除令牌外的字段（名称 / 协议 / 地址 / 启用）都是**表单态**，只有落库后才会被适配器看到。
「验证协议」「验证地址」「拉取模型」都先**把表单当前内容落库**再发请求，即**验的是屏幕上这一份配置**。

- 这条规则是补缺陷补出来的：`verify` 原先只读**库里已保存**的 protocol，于是「把协议切到 OpenAI 兼容 → 直接点验证地址」会静默拿旧协议（mock）去验，表现为「秒过」却一个请求都没发——地址填了也白填。顺序语义不能靠用户猜，只能由按钮承担。
- 表单同步只在**切换渠道**时发生，不跟随 store 的每次后台更新。否则「验证协议」命中后回写 `protocol`、启用开关回写 `enabled` 都会产生新的渠道对象，把用户刚选好的协议静默弹回库里旧值（看起来就是「选了又跳回去」）。
- 「验证协议」是这条规则的**唯一例外方向**：命中后要把结果**同步回表单**（`setProtocol(hit)`）。探测的全部意义就是替用户把「协议」那一格填对；只在库里写、表单不动，用户看到的下拉还是旧值，等于没自动选。

#### 状态行：必须说清「这次是谁、做了什么、结果如何」

状态行对**当前选中的渠道 + 最近一次动作**负责，文案按动作分叉（三个按钮问的是三个不同的问题，不共用一句话）：

| 动作 | 成功 | 失败 |
| --- | --- | --- |
| 验证地址 | `✓ 地址可达 · OpenAI 兼容 · 生图 · 137ms` | `✗ <分类里的可读原因>` |
| 验证协议 | `✓ 已识别协议 · OpenAI 兼容 · 生图` | `✗ 未识别出协议 · <最后一条失败原因>` |
| 拉取模型 | `✓ 已拉取模型 · OpenAI 兼容 · 生图 · 发现 12 个模型` | `✗ 拉取失败 · <原因>` |

- **协议名必须出现在结果里**：mock 下与真实中转下「通过」长得一模一样，用户无法判断这次到底出没出网。
- **延迟由发起方测、并落库**：适配器只管通不通，不知道调用方何时开始等；`lastTestAt` / `lastTestLatency` 由 store 在发起前后取墙钟差（含 DNS / TLS / 响应体），与用户按按钮的体感一致，且刷新后仍可回溯。失败路径不展示延迟（那一行要留给错误原因）。
- **mock 通过时给出显式提示**：mock 是离线协议，不发任何网络请求、也不访问所填地址；提示中指明「要联调真实中转，把协议切到 OpenAI 兼容 · 生图，或直接点『验证协议』让它自己认」。
- 「拉取模型」「验证地址」「验证协议」共用这条状态行，失败同样有反馈——此前「拉取模型」没有 catch，地址错时抛成未捕获拒绝，用户点了按钮什么反应都没有。

#### 失败提示分类

失败文案在**适配器层**由归一化错误（`AppError`）推出，不由 UI 拼装；平台层抛的**不是 Error 实例**（网络端口抛 `AppError` 字面量、渠道层抛 `ChannelError` 且载荷在 `appError` 上），故取值前统一过 `asAppError()`——否则会渲染成 `[object Object]` 或泄漏内部调试串。

**文案一律中文、不露标识符**（用户 2026-10-05 第 3 批：「他显示报错的时候能否把中文发我，而不是代码」）：`describeError` 里给 `network.detail` / `storage.detail` / `channel.detail` 各配一张中文表（`cors` → 被对方跨域策略挡下、`missingKey` → 还没填令牌、`quota` → 本地空间不够……），HTTP 那条改成**中文打头 + 服务端原话**（`服务端返回错误（HTTP 402）：预扣费不足`），拿不到原因时说「而且没给原因」，不再只丢一个裸状态码。agent 循环里的 `errText` 也**先过 `asAppError → describeError`**：渠道层抛的是 `{kind,status,body}` 字面量，不翻译就会一路落到 `JSON.stringify`，把 `{"kind":"http",…}` 原样贴进对话。**新增一种错误取值时，映射表要同步加一行**（单测遍历全部取值 + 断言不出现英文标识符）。

| 错误 | 提示 |
| --- | --- |
| 401 / 403 | API Key 无效或无权限 |
| 404 | 端点不存在，检查地址与协议 |
| CORS 失败 | 跨域被拦截，中继需开放 CORS |
| 网络层失败（解析失败 / 连接被拒） | 连不上这个地址——核对地址、确认中继可达 |
| TLS 失败 | TLS 证书错误（证书不受信任） |
| 超时（> 10s） | 请求超时，服务无响应 |

#### 开关：隐形原生 checkbox，不裁切成 1px

「已启用」由轨道式开关呈现，但**原生 checkbox 保留在与轨道等大的命中层上**，只把 `opacity` 设为 0。
不要用 `clip: rect(0 0 0 0)`（或把它缩成 1px）来「隐藏」它：那样自动化工具的可见性判定会失败，
`check()` **静默不生效** —— 渠道没被真正启用，画布侧就误报「没有选择渠道」。
保留命中区同时意味着键盘焦点、无障碍语义都不用另造一套。教训见 `.workbuddy/memory/MEMORY.md`。

### 7.4 右侧：模型管理 · ✅ 已实现

**标题区**：第一行「模型列表」，下方小字「从上游 api 自动拉取所有可用模型」，右侧两个按钮「拉取模型」「选择模型」。

**拉取模型面板**

| 元素 | 说明 |
| --- | --- |
| 分类选项 | 全部 / 生图 / 对话 / 视频 |
| 搜索框 | **不提供**（用户 2026-11-16 明确删除模型搜索） |
| 默认状态 | 拉取到的模型默认全部未勾选，由用户自行勾选 |
| 应用 | 面板右下角「应用到模型列表」，点击后面板关闭 |
| 缓存 | 拉取过的模型读本地缓存，需要刷新时显式重新拉取 |

**已选模型展示**

```
生图模型   (gpt-image-2 ×)  (flux-1 ×)
对话模型   (gpt-5.6 ×)
视频模型   (veo-3 ×)
```

每个模型右侧有删除按钮。「选择模型」可再次打开面板勾选此前未选中的模型。模型标签使用统一的浅色胶囊样式。

**实现说明**

- **「拉取」与「已选」是两份数据，这是本节的骨架**：`modelCache` = 拉回来的全部（选择面板的数据源），`models` = 用户勾过的那几个（**画布 / 漫画的模型下拉只读这一份**）。二者此前合一，于是「拉回 200 个模型、下拉就列 200 个」，用户没有任何筛选手段——「已选」这个概念本身不存在。
- **面板是草稿态**：勾选先记在本地，点「应用到模型列表」才落库。中途取消不写半成品（与画布「编辑中不落库」同一口径）。打开面板时**此前已选的保持勾上**。
- **应用时的两条口径**：①命中缓存的以缓存为准（模型能力可能在上游更新过，勾选动作顺带吃到新能力——能力驱动参数显隐，留旧快照会让新参数永远不出现）；②**缓存里已消失但仍勾着的保留**，上游改名不该把用户的选择静默清掉，它仍出现在已选行里、可由 × 去掉。
- **验证/拉取都不会替用户勾选**：`verify` 通过只写 `modelCache`。顺手全选等于把选择权从用户手里拿走，且下一次拉取会继续替他选。因此「新配渠道 = 已验证 + 零已选」是**默认状态**，界面必须显式说清（见下）。
- **空态分三种、文案必须不同**：①没拉过（「还没有拉取过模型」）；②拉过但一个都没勾（「上游有 N 个模型，但还没勾选任何一个」——这是新渠道的默认状态）；③已选若干（三行分组）。三者混成一句「暂无模型」，用户不知道该点「拉取模型」还是「选择模型」。
- **下游空态同步补齐**：渠道已启用但没勾模型时，生成节点与创作面板都给出可点击出口（节点写「去选模型」、面板写「该渠道还没勾选模型 · 去后台设置 →」）。原因不是体贴——`toRunRequest` 在 `model` 为空时返回 `null`，该节点**直接不进执行计划**，用户点生成**毫无动静**。这类静默失败必须由界面显式承担。
- 分类与筛选口径住在 `domain/project/modelSelection.ts`（纯函数 + 单测）：分类过滤、关键字过滤、分组顺序、应用时的新旧合并都在那里。**在界面上看不出对错**的东西（勾错了只是「列表长得不太一样」）必须由单测钉住。

### 7.4.1 模型映射 · ✅ 已实现（M7-1..M7-5，2026-09-26 ~ 09-27）

**问题**：不同中转站对同一模型的名字不一样（例：A 站叫 `gpt-image-2`、B 站叫 `image-2`），而画布上暴露的模型名应当是**稳定的**。若节点直接存上游模型 ID，换渠道就得改遍所有节点；同一个「逻辑模型」在不同站点也无法复用。

**目标**：节点上暴露**固定逻辑名**，后台为每条渠道配置「逻辑名 ↔ 上游模型 ID」的映射；生成时按当前渠道把逻辑名翻译成该站的真实 ID 再发请求。

**设计要点**

| 项 | 口径 |
| --- | --- |
| 逻辑名 | 画布 / 漫画的模型下拉显示与节点存储的**唯一名字**；与站点无关，跨渠道稳定 |
| 映射表 | 每个 **Key 分组**各有一份 `modelMap: Record<逻辑名, 上游ID>`；渠道级 `modelMap` 只保留为老数据兼容聚合。可在当前分组内编辑 |
| 默认映射 | 拉取模型后若逻辑名与上游 ID 同名，自动建立恒等映射；不同名则留空待用户填 |
| 解析时机 | 执行计划构造请求时解析（`逻辑名 → 上游ID`）；解析不到就**如实报错**，不静默回落到别的模型 |
| 与已选模型的关系 | `modelMap` 决定「这个名字发出去时该用哪个上游 ID」。**2026-10-08 起画布下拉只列前端显示名**（方案 A，对账 #371 —— 渠道拉回来的名字一律不进列表）；选路时「渠道提供该模型」既认 `models` 里的同名项、也认 `modelMap` 里的键，所以列表里没有渠道模型**不影响它能不能跑** |
| 后台映射区列什么 | **列当前分组已勾选的真实模型**，每个真实模型一行；右侧选择它服务的全局前端模型。不同分组可以把相同或不同的真实 ID 映射到同一个前端模型 |
| 兼容性 | 无映射时沿用当前行为（逻辑名即上游 ID），老项目与老渠道零迁移 |
| 存储 | 仍是 `channels` 表内字段，不新增表；读回按「只补不删」补默认值 |

**映射区的分组与填法（用户 2026-09-27 二轮）**

| 项 | 口径 |
| --- | --- |
| 展示 | 不再按前端目录平铺，也不再使用映射分类筛选。三列是“真实模型 / 对应前端模型 / 全局常用状态”；不设固定映射状态列，也不放逐行测试按钮 |
| 说明文案 | 映射区**不放说明段**（用户 2026-10-08：「这个框住的文字可以删掉了」，指"左边是画布里显示的名字…"与"左边是画布里可选的显示名…"两行）。区块标签「模型映射（前端显示名 → 本站点真实 ID）」保留 |
| 填法 | 从当前分组的已选真实模型出发，用下拉选择同类全局前端模型；保存即写当前 Key 分组。未登记到全局目录的旧值显示为“待绑定”，不会冒充已完成的映射 |
| 候选来源 | “对应前端模型”下拉只列全局前端模型目录中同分类的目标；“当前分组真实模型”来自该分组已勾选的 `models`，两者不再混成同一个下拉 |
| 为什么给下拉 | 上游 ID 是站点自己的命名，用户基本记不住；而它**本来就躺在已勾选的模型清单里**。让他在两处重复输入同一串字符，是把「选择」做成了「默写」 |
| 旧值兼容 | 旧渠道已有、但目标名不在当前全局目录中的映射值会标为“待绑定”并保留；重新选择全局前端模型后才算完成 |

**候选菜单的 UI 与生图节点参数同源**（用户 2026-09-29 第 13 轮「我要制作成生图节点参数的菜单那种 ui 样式」）：

浮层沿用 `ParamPicker` 的视觉口径（`--bg-surface` 底 + 1px `--stroke` 描边 + `--radius-control`、**无投影**、

#### 选路策略是全局的（用户 2026-09-29 第 12 轮）

**用户口径**：模型**映射**确实每条渠道都要配（各站模型 ID 不同），但**选路规则**
是「同一个模型在多条渠道都能用时挑哪条」，这是**跨渠道**的事，不该塞进某一条渠道的表单里。
名称沿用项目里已有的「**选路策略**」。

| 项 | 口径 |
| --- | --- |
| 位置 | 全局顶栏，横跨左右两栏、位于两栏工作区之上（`.layout` 直接子节点、`.workarea` 之外），不属于任何渠道表单；**未选中渠道也能设置**（第 13 轮从编辑区移出，消除「像右边渠道表单里的一项」的观感） |
| 存储 | `presets` 表保留行 `routing:strategy`（与生成配方同表、不同前缀）；非法值 / 缺字段 / 读失败统一回落 `priority` |
| 与渠道的关系 | 候选渠道各自带 `priority` / `weight`（衡量**这条渠道本身**），策略只决定**怎么比较这些候选**；旧 `routeStrategy` 字段仅兼容、不再读取 |
| 禁用即不参与 | **渠道未启用 = 绝对不参与选路**。候选硬过滤 `enabled && hasToken && upstreamModel`，禁用渠道即便优先度最高、权重最大、延迟最低也不入选；全部禁用时报错而不是硬发 |
| 价格 / 质量优先 | **继续推迟**：项目里没有价格表与质量评分，做了只是假排序（同架构文档 §6.3）。数据就位后给 `RouteStrategy` 加枚举值即可，解析函数不用改结构 |
