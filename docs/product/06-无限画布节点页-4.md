### 6.23 图像融合节点 · ✅ 已实现（2026-09-29）

**一句话**：图像融合节点把一张**完整原图**和若干张**局部修改图**在**本地**做像素合成，
输出一张新图给下游。它自己不调任何渠道模型，也不产生任何网络请求。

> 需求来源：用户 2026-09-29 参照「大雄无限画布」的 `local-patch` 融合节点提出，并明确
> 「我不是要插件格式，我要把那个节点做成我项目中的节点」。因此本节点是轻画**原生节点**
> —— 进 `NodeType` / `NodeSpec` / 视图注册表 / 工具栏，**不引入插件运行时**，
> 也**不读取**大雄插件的插件目录。本文抄的是概念与像素算法口径，实现按轻画的分层与命令式架构重写。

#### 为什么它不是「生成类节点」

| 维度 | 生成类节点（prompt / generation / …） | 图像融合节点 |
| --- | --- | --- |
| 是否调渠道 | 是，构造渠道 `RunRequest` | **否**，纯本地像素运算 |
| 是否进 `isGeneratableType` | 是 | **否**（不得加入） |
| 产物来源 | 上游模型返回 | 本地 canvas 像素合成结果 |
| 失败面 | 网络 / 配额 / 模型 | 输入缺失 / 尺寸与比例校验 |

把融合节点当生成类处理，会把它错误地拖进选路、重试、配额统计等与它无关的逻辑，
故本节单独定死这条边界。

#### 数据模型（`FusionData`）

| 字段 | 含义 |
| --- | --- |
| `contexts` | 选区上下文列表，按提取顺序存储，1–16 条；未提取任何选区时为空数组 |
| `activeContextId` | 当前在节点内预览/编辑的选区 id；无选中为 `null` |

`FusionContext` 的形状（**已落地**，字段以代码里的类型为准）：

| 字段 | 含义 |
| --- | --- |
| `id` | 本次裁切上下文的稳定 id |
| `source` | `{ assetHash, width, height }`：原图素材 hash + 像素尺寸（不存 url：url 是 `useAsset` 按 hash 临时造的 objectURL，存下来刷新就失效） |
| `rect` | `{ x, y, w, h }`：用户框选的局部修改区（原图像素坐标，整数） |
| `paddedRect` | 参与合成与羽化的**外扩**矩形（宽高各乘 `1 + 2 × paddingRatio`，比例与 `rect` 完全相同） |
| `paddingRatio` | 外扩比例，默认 `0.1`（与大雄插件同值） |

> 早先设计稿里的 `version` / `fingerprint` 没有实现，**故没有留在类型里**：
> 「版本号」是给已经存在的数据用的迁移手段，而这个结构还没有第二版；
> 「内容指纹」在这个语义下与 `assetHash` 重复（hash 就是按字节算的）。
> 留一个永远等于 `2` 的字段、和一个从不参与判断的指纹，只会让人以为它们在起作用。

#### 提取选区：上下文**跟着图片走**（2026-09-29 落地）

用户口径：「图片素材，点击提取选取后，在**素材的灯箱预览界面**框选局部图，框选有比例的限制，
比例的限制在素材灯箱界面；框选后的局部图**带持久性的上下文**，通过模型进行改图后也有上下文，
能支持**多轮改图**」。参考实现（`local-patch`）也是这个骨架，而且它明确**复用宿主的裁剪编辑器、
不另做裁剪器**（版本记录 v2.0.1 / v2.1.0 两条都写了「插件入口应复用原项目已经存在的交互位置」）。

| 项 | 定稿 |
| --- | --- |
| 入口 | 图片节点的**上方功能栏**（有素材才出现）+ **右键菜单**（与「保存到素材库」同一条件）。有素材就能提取，**与节点类型无关** —— 生成节点、融合产物（它也是一张图）都可以 |
| 框选界面 | **素材灯箱**（§6.17）的「提取选区」模式：拖框 + 比例档（九档 + 自由，与融合节点共用 `ratioChoices`）+ 取消 / 提取选区。灯箱原有的滚轮缩放 / 平移仍然可用（选区存**原图像素坐标**，缩放平移不会让它漂）。**比例档与两个按钮在同一组里**（同一排、紧挨着），不摆到工具栏两头 |
| 框选**二次修改** | ① **框内拖动 = 平移选区**（尺寸一分不变、位置跟着走、出界只夹）：框好之后最常见的动作是微调位置，首版把「按在图上」一律当成画新框 ⇒ 一点就重画（用户 2026-09-30：「在选取内拖动每次都会新建一个选取」）。② **8 个手柄**（四角 + 四边）继续拖：拖哪条边就动哪条边、**对面那条边钉死**；比例档在位时按**同比例**缩放（单拖一条边也会把另一轴推出去 —— 不然一拖就破比例，而补丁是按模型比例出的图，融合会被比例校验直接拒掉）；短边守 32px 下限；指针滑出图外只**夹**不缩 |
| 产出 | 在**原图右侧**新建一个「局部图」节点：按**外扩矩形**裁出、存成**新素材**，**原图一个字节都不动**；一次提取 = 一步撤销 |
| 上下文 | `GenerationData.cropContext`：`Omit<FusionContext,'id'>`（局部图：属于哪张原图、哪个矩形、外扩矩形）或 `{ full: true }`（**完整图边界**） |
| 传播 | `resolveCropContext(nodeId, graph)` 沿上游 BFS 解析，因此**中间套几层改图都不会丢**；碰到 `full` 就停（融合产物不许继承上一轮选区，否则第二轮会挂错位置）；收集到**多个不同选区** ⇒ `conflict`，**拒绝融合、不猜来源** |
| 融合怎么用 | `fuseNode` **优先用局部图自带的上下文**；没有才退回「融合节点里框的选区（按连线顺序配对）」—— 两条路并存，老数据不会坏。视图的「能不能点融合」也按同一判据（`InputPortAsset.hasContext` 由画布表面注入） |

**选区上下文住在融合节点的 `data` 里，不进 `assets` 表**：它描述的是「这次合成怎么取像素」，
不是一份可被其它节点当素材复用的资源。写进 `assets` 表会把过程数据污染成产品数据。

#### 裁剪：同一套框选，产出**不带上下文**的一块（2026-10-17 / 对账 #553）

用户口径：「节点功能区需要加一个裁剪功能（相当于不带上下文的提取选区图）」，
动机是融合节点对**带上下文的局部图**有要求，而有时他就是想切一块图去做别的事。

| 项 | 定稿 |
| --- | --- |
| 入口 | 图片节点的**上方功能栏**（有素材才出现）+ **右键菜单**，**紧挨着「提取选区」**（同一条件、同一分组） |
| 框选界面 | 与提取选区**完全同一个**灯箱框选模式（拖框 / 八向手柄 / 比例档 / 取消 / 确认）。区别只有两处：底部模式条这一档的文案是「裁剪」，操作条上多一句说明「裁剪不带选区上下文，融不回原图」 |
| 几何 | **按用户框的原样切**（`paddingRatio: 0`）。提取选区那条是外扩 ×1.2 —— 外扩是给模型留上下文、给羽化留余量的，而裁剪没有融合那件事，多留一圈只会让「我框的」和「出来的」对不上 |
| 产出 | 在原图右侧新建一个**「裁剪图」**节点（名字与「局部图」刻意不同，一眼能分清手上这块是哪种） |
| 上下文 | 写 **`{ full: true }`（完整图边界）**，**不是"不写字段"**。字段缺席时 `resolveCropContext` 会一路往上游穿 ⇒「从一张局部图上再裁剪」会莫名继承上一层的选区 ⇒ 那张裁剪图会被当成"属于原图某一块"的局部图，融合时挂到不相干的位置上。边界标记才会停住 |
| 能不能当融合补丁 | **不能**。`fuseNode` 要求每张补丁自带选区上下文，裁剪图会被明确拦下，并且提示原文点名这件事（「用「裁剪」得到的不带上下文，融不回去」） |

**为什么不做成「提取选区」上的一个开关**：同一个按钮产出两种语义（一种能融回原图、
一种不能），而"能不能融"取决于一个**看不见的开关状态** —— 这正是本项目一直在防的
「看起来通了」。两个入口，各自语义单一。解释性文案落在**用户撞墙的地方**
（融合节点那条提示），而不是藏在裁剪面板里 —— 用户在点"裁剪"时并不在融合的上下文里。

**写与读是两处，各要一条断言**：`cropContextFor`（写：裁剪一律写边界）与
`resolveCropContext`（读：碰到边界就停）分开实现。只测读那一侧会漏掉
"我们到底写没写" —— 实测把 `{full:true}` 换成不写字段，端到端冒烟**照样绿**
（裁剪节点是浮动的、没有入边，解析根本走不到上游），所以那条差别必须由
能构造「局部图 → 裁剪图」入边的单测来守。

#### 一个生成节点吃两张「局部图」= 两处位置混进同一张产物（2026-10-17 / 对账 #558）

这是用户实测出来的一个反直觉点，必须写进产品口径：

> 图1 提取出「图1-2」（带"贴回图1"的选区），图2 提取出「图2-2」（带"贴回图2"的选区），
> **两张一起**交给同一个生成节点改图 → 产物同时带着**两处**位置 ⇒ 融合拒绝猜，如实报
> 「混了多个不同的选区」。他把「图2-2」换成**裁剪**块（不带上下文）之后就能融了。

**为什么这样才对**：融合的补丁必须唯一地知道"贴回哪里"。一张产物如果同时带着两处位置，
任一选择都是猜；猜错就是把像素贴到不相干的地方，而画面上不一定看得出来。所以宁可拒绝。

**两种意图，两种画法**：

| 你的意图 | 正确画法 |
| --- | --- |
| 两处都要改、都要贴回去 | 两张局部图**各自**改图（各自一个生成结果），再分别接到融合节点右侧的共用口 —— 每个补丁只带**一个**自己的上下文 |
| 一处要改、另一处只是**参考** | 参考那一路**不要带上下文**：直接用原图，或用「裁剪」裁出来的那块。这样产物的上游只剩一个上下文 |

> **提示必须点出"是哪几处"**：`resolveCropContext` 的冲突分支现在把收集到的上下文一起带出来，
> `conflictReason` 拿 `context.source.assetHash` 反查原图节点的**标题**（重名时补短 hash），
> 于是用户看到的不是"混了多个"，而是"它同时带着「图1」「图2」这几处的位置"，
> 并且直接给出上面那两条出路。

**「修改后的局部图要持久性地保持上下文、能反复修改」靠两条落地**：

1. **上下文随节点持久化**：`contexts` 是节点数据的一部分，刷新 / 重开项目 / 复制粘贴
   都还在（与提示词正文同级，不是运行时状态）。
2. **补丁与选区的映射是位置映射**：**第 i 条 `patch` 入边 ↔ 第 i 条上下文**，按连线顺序。
   上游修改图**重新生成**（用户「再改一次」）之后连线的位置没变，于是同一个选区
   自动对上新的补丁 —— 不必重新框选。刻意不做「每条上下文记住自己的补丁节点 id」：
   那种写法在换线 / 复制粘贴 / 删掉重建节点之后会留下指向不存在节点的悬空引用，
   而位置映射天然跟着图走。

**换原图要认得出旧选区**：每条上下文记着 `source`（原图 hash + 像素尺寸）。
上游原图被换成另一张之后，旧选区的坐标落在新图上就是**错的位置**——
`contextMatchesSource` 把这类选区识别出来、融合按钮如实提示「原图换了，请重新框选」，
而不是默默把补丁融到不相干的地方。

#### 端口：左「原图」+ 右「局部修改 / 输出」**共用一只口**

**这是本项目第一个「不止一对口」的节点**，端点因此从「布尔对」升级成**声明**
（`nodeSpecs/ports.ts` 的 `PortDecl`：id / kind / side / 纵向比例 y / 是否允许多条）：

| 端口 id | 位置 | 方向 | 语义 | 数量 |
| --- | --- | --- | --- | --- |
| `input` | 左边缘中点 | 入 | 接一张**完整原图** | 恰好 1 条入边（沿用去重） |
| `patch` | 右边缘中点 | **入 / 出共用** | 入边接 1–16 张**局部修改图**（允许同源多边）；出边把**融合结果**交给下游 | 入 1–16 条、出 0–N 条 |

用户口径：「**右边只需要一个端点**，可以连接多个局部图」。这与参考实现一致 ——
大雄 `local-patch-classic.js` 里那只点同时带 `in` 和 `out` 两个类、
`data-target-port="patch"`，它的 `mousedown` 直接就是 `startLink(..., 'out')`。

于是 `PortDecl.kind` 多了一个 `'both'`：**同一个锚点既是入也是出**。规则是
「**从这只口往外拖 = 出**；上游出线落在**节点右半边** = 进这只口」——
落点按「离指针最近的输入口」判定（左半边是原图口、右半边是这只共用口）。

- 默认那对口的 id 刻意沿用历史值 `input` / `output`（**不是** `original`）：冒烟选择器
  与既有断言都按 `[data-port="input"]` 定位，改名等于把它们全部改红。
  融合节点**关掉默认的 `output`**（否则右侧又变成两个点），右口在 `extras` 里声明。
- `patch` 声明的 `multi: true` 只对**入方向**生效：同一个上游连两次就是
  「两张局部修改图」，按端到端去重会把用户的第二次连接静默吃掉；出方向本来就能连多个下游。
- `Edge` 补 `sourcePort` / `targetPort`（**可选**：缺省即历史口径，老数据零迁移），
  去重键从 `(source,target)` 改成 `(source,sourcePort,target,targetPort)`；
  复制粘贴 / Alt 复制都把端口一起带上（丢掉端口会让两条边退化成同一条）。
- **拖线落点按「离指针最近的那只输入口」判定**：节点可能有两只输入口，而松手只给出
  一个节点。只有一只候选时就是它 —— 与历史行为完全一致。
  从 `patch` 口**反拖**（从入口找上游）是最精确的接法；正拖到节点右半边也会落到 `patch`。

#### 合成顺序与算法口径

| 步骤 | 口径 |
| --- | --- |
| 取原图 | 按 `context.source` 取原图位图；原图缺失或指纹不符时报错，**不静默降级** |
| 取补丁 | 按连线顺序依次读取每条 `patch`；某条读失败即整次失败，不做部分合成 |
| 重采样 | 补丁缩放到 `paddedRect` 尺寸，用 `imageSmoothingQuality = 'high'`（浏览器能开到的最高一档，最接近 Lanczos） |
| 比例校验 | 补丁长宽比与 `paddedRect` 长宽比失配 **> 1%** 即拒绝（避免拉伸变形）。拒绝时必须**把两个尺寸都写出来**（2026-10-17 / 对账 #555）：「选区 240×240，修改图 1024×1024」—— 只说"比例不一致"用户手里只有两张图，无从判断该重裁还是该把模型比例调成「跟随素材」 |
| 羽化 | 逐像素解析剖面：`smoothstep(min(到最近横向边的距离, 到最近纵向边的距离))`，再叠 **0.8px 模糊**，最后把**选区内部补回纯不透明**（模糊会从选区边界往里啃一圈，不补就把选区自己的像素啃淡了） |
| 模糊 | 见上：0.8px，作用在**遮罩**上而不是画面上（糊画面等于把内容一起糊掉） |
| 色彩匹配 | 取外扩框里**挖掉选区**的那一圈（`ring`），算原图与补丁各自的均值，差值按通道**夹在 ±24** 后加到补丁上。多张补丁依次合成时，参考色取**当前已合成的那张图**，不是原始位图 |
| 覆盖 | 后处理的补丁覆盖先处理的；**输入素材本身永不被覆盖** |
| 输出 | 合成结果作为本节点输出交给下游 |

> 羽化的「取两边距离的**较小者**」不是随手写的：若写成两者**相乘**，四个角会各淡一次
> （角上明显比边更透），而「离选区边界多远」本来就该由最近的那条边决定。
> 单测用「横竖不同距离」的点把这两种写法区分开。

#### 外扩：等比 + 滑回图内 + **必须完整包含选区**

`paddedRect` 的宽高各乘 `1 + 2 × paddingRatio`（默认 **0.1**），然后整体**平移**回图内
（不是裁掉出界的那一边）。这三条一起构成「贴边选区」的解法：

1. **等比**：`paddedRect` 与 `rect` 比例完全相同。首版按「相对短边加一圈」实现，
   一个 16:9 的选区外扩后比例变成约 1.67，而模型是按用户选的 16:9 出图的 ——
   回来一比就超 1% 容差，**每一张补丁都会被比例校验拒掉**，功能等于不可用。
2. **平移**：外扩必然出界，裁掉会让羽化边缺一条、接缝变成硬边；平移保住矩形完整，
   代价只是合成位置整体内移几像素。
3. **完整包含选区**：窗口任何一条边都不许落在选区里面。这条最容易被**取整**破坏 ——
   选区顶满图宽时，`round(w × scale)` 可能算得比选区窄 1px，于是羽化剖面里
   「选区右边界」跑到窗口之外，水平方向直接退化成不羽化。

> 这三条**逐行对齐大雄无限画布 `local-patch` 插件的 `compute_padded_rect`**
> （连 `max(rect.w, round(rect.w × scale))` 那个夹取都照抄）。它源码里的注释把第 1 条
> 的原因写死了：「A simple boundary clamp removes padding from only one axis/side and
> changes the ratio whenever the selection is close to an image edge. Instead, size the
> context window uniformly and slide it back inside the image.」
> 它那边有 `test_padding_preserves_non_square_ratio_at_all_edges` 逐位置扫边界，
> 本实现也照抄了一条等价单测（比例 + 包含 + 不越界三条一起断言）。

#### 参数与限制

| 项 | 值 |
| --- | --- |
| 补丁数量 | 1–16 张；**必须与选区数相等**（不等即拒绝并说明哪一边多了） |
| 选区总像素上限 | `100 MP`（超过即拒绝，防浏览器内存爆掉） |
| 最小选区边长 | `32 px`（按外扩后的矩形算 —— 用户框得略小一点时外扩可能刚好够用） |
| 比例失配阈值 | `> 1%` 拒绝 |
| 外扩比例 | `0.1`（宽高各 ×1.2）；上限 `0.5`，且**必定夹到「装得下选区又不越界」** |
| 色彩匹配 | 每通道最多 ±24；**参考环 = 外扩框挖掉选区**的那一圈 |
| 颜色匹配开关 | 节点底栏的复选框（参考实现的融合卡片上也是这个开关），**默认开**；关掉时连 `getImageData` 都不做 |
| 原图对应关系 | 上下文记的 `assetHash` + 像素尺寸都要与当前原图一致；不一致的选区视为失效，提示重新框选 |

#### 缺失输入时不占提示空间（2026-10-25 修订）

`original` 或 `patch` 任一为空时，只禁用「开始融合」按钮，不在卡片里渲染提示条，也不为提示预留空间。
只有真实执行错误（例如局部修改图缺少选区上下文）才显示错误区域；错误正文可以换行，展示具体原因。

#### 交互与视觉定稿

| 项 | 定稿 |
| --- | --- |
| 端口 | **两只**：左中「原图」入口；右侧一只**共用口**（入 / 出同一锚点，画成环形以便与实心的入 / 出点区分）。锚点圆心落在节点边框上（半个圆在外） |
| 颜色匹配 | 底栏左侧的圆角描边按钮，**默认开**；平常态无填充，选中态深色填充 + 浅色文字。它在「合成顺序」里是独立的一层：关掉只是不上色偏补偿，羽化照常 |
| 卡片结构 | 上「原图 \| 局部修改」两块正方预览（各自带深色胶囊标签）→ 连接状态胶囊（✓ 原图 / ○ 未连接局部修改 0 张）→「颜色匹配」+「开始融合」同一排；开始融合收缩到剩余宽度，无图标、深色填充。缺输入不显示提示条，真实错误才长出错误区域 |
| 局部修改预览 | **左边原图、右边局部列**（参考图：用户 2026-09-30 给的大雄融合卡片截图，「铺满 + 左右分区」）。① 局部图**上下排列**、不朝右横向长：横向铺开会把节点越撑越宽、把左边原图越挤越小。② 预览区**吃掉节点里的剩余高度**（`.panes` 是 `flex: 1 1 auto`），右列与左格等高、每张等分 ⇒ 张数变多只让每张变小，**容器尺寸不变**；贴到可读地板（44px）后改为**列内滚动**（参考图右列就有细滚动条），不压成一条缝。③ 两块都用 `object-fit: cover` **铺满**（上一版原图用 `contain` 是为了「别裁掉原图」，结果上下留白，与参考图不符）。④ 标签「原图」/「局部 1」/「局部 2」——**始终带序号**，几张并排时序号是唯一能跟连线顺序对上的东西。⑤ **双击任一格进灯箱看大图**（与生成节点同一事件口径 `emit({ type:'openLightbox' })`）。一张都没有时是灰底 + 占位图标 |
| 选区在哪 | **只在图片上**：在图片节点的素材灯箱里「提取选区」得到（见上一小节）。融合节点里**没有**框选 UI、没有选区芯片、也没有比例芯片 —— 那一整套都删了（用户：「之前的那个东西删掉，都不对」），因为它建立在一个错误前提上：**选区属于图片，不属于融合节点** |
| 卡片尺寸与内边距 | **内容跟节点**（与循环节点「节点高度跟内容」相反，别照搬）：预览区 `flex: 1 1 auto` 吃掉剩余高度，左右两块填满各自格子；**不做**任何「量内容高度写回节点」的 `ResizeObserver` —— 那会与手动拉右下角互相顶，表现为放大后松手再跳一下（2026-09-30 实修，实测 306 → 332）。内边距四边同档 `--space-3`（12）：预览块是贴边的大色块，上下 8 / 左右 12 那种通用写法在这张卡上看着就是不齐。节点的拖动把手用连接状态那一行（`[data-fusion-chips]`）—— 内容区域留着将来加点击放大之类的交互（与循环节点「控件不兼任把手」同一套取舍） |
| 产物落点 | 融合成功后**在融合节点右侧新建一个「融合结果」节点**并连上（从共用口出），**不写回融合节点自己**；反复融合按已连出的结果数往下排格。结果节点写「完整图边界」，因此可以再提取下一个选区 |
| 修改图 ↔ 选区映射 | 第 i 条 `patch` 入边 ↔ 第 i 条上下文（连线顺序）；补丁长宽比与 `paddedRect` 失配 > 1% 即拒绝。**选区数与补丁数不等也拒绝**，并说明是哪一边多了 |
| 多选区同步融合 | 允许多个修改后的局部选区图**同时**参与一次合成，按连线顺序后者覆盖前者；一次运行 = 一步撤销（`beginPlan` / `endPlan`） |
| 输出与对比原图 | 产物尺寸 = **原图尺寸**（「同一张图、局部变了」），像素读数挂在节点外右上角（与生成节点同一口径）。**对比原图在灯箱里**（用户 2026-09-30：「融合节点出的结果图双击出现灯箱后要有对比原图的功能」）：产物节点写 `GenerationData.compareWith = 原图的 assetHash`（产出那一刻的既成事实，不靠连线反推），双击产物进灯箱后顶部操作区给出三档「结果 / 对比 / 原图」——「对比」把原图叠在结果上、按可拖的分割线裁左半边（与对比节点 §6.10 同一形态），拖动只改本地瞬时值；读不到配对时不出现该入口 |
| 运行入口 | 节点底栏的「开始融合」文字按钮 + 跟随栏的「生成」按钮 + 右键菜单，全部走 `runNode` 的同一条分支 —— 入口多一条就少一处不一致 |
| 融合失败 | 真实失败一律说明原因（缺上下文 / 比例不符 / 素材读不出来 / 选区太小），**不静默返回**；缺原图或补丁时只禁用按钮，不占卡片提示空间 |
| 边缘选区 | 选区贴边时先外扩 `paddedRect`、再平移回图内并保持长宽比，避免羽化边被裁掉（对齐大雄插件的处理） |
| 浮层不裁剪 | 比例浮层要越出节点底边：`NodeFrame` 对 `[data-fusion-node]` 放开 `.body` 的 `overflow`（与循环节点同一处理，`clip` 会把档位点不到） |
| 自适应高度 | 节点高度跟随内容（预览 + 选区行 + 补丁行 + 底栏）由 `ResizeObserver` 写回；去掉某一行时不得留大片空白 |
| 文字溢出 | 提示文案、比例标签都能换行或省略，不得溢出节点容器 |
| `+` / `×` 图标 | 用对称矢量 SVG，不用文本字形；圆钮容器 `grid + place-items:center`，确保图标中心与圆钮中心重合 |
| 选中态 | 沿用循环节点的 `--node-contrast-*` 口径：浅色黑底白字，深色浅底深字；主操作按钮（融合）与颜色匹配选中态共用该令牌 |
| 缩放清晰度 | 画布世界层不得写 `will-change: transform`（同 §6.22） |

#### 与现有规则的关系

| 规则 | 说明 |
| --- | --- |
| 生成类判定 | **不得**加入 `isGeneratableType`；不参与选路、重试、配额 |
| 撤销 | 一次「运行融合」= 一步撤销（沿用 `beginPlan` / `endPlan` 口径） |
| 连接合法性 | 端口规则见上；`patch` 允许同源多边，`input` 沿用去重，`output` 不接受入边；沿用 `topoSort` 环检测 |
| 产物落位 | 融合结果**落成一个新节点**（§6.23 交互表那行），并从共用口连过去；输出**不覆盖**任何输入素材，也不写回融合节点自己 |
| 各下游的 `accepts.upstream` | 融合产物是「一张普通图片」，故 `prompt` / `generation` / `compare` / `group` / `batch` / `loop` / `fusion` 全部加上了它。**这一类「少一个」的缺陷读代码发现不了**（表现为「连不上、也不报错」），按记忆里的新增节点接线清单逐项过 |
| 执行路径 | 不走 `runEngine`：它每一步都在等一个网络往返，而这里只是几张位图叠一叠。融合是宿主的**独立流程**（读素材 → 合成 → 落库 → 写回），在 `runNode` 里单开一条分支 —— 与循环节点 / 批量的分发分支并列 |

### 6.24 画布助手（Agent 对话窗） · ✅ 已实现（2026-10-01）

一句话 → 画布上真的长出一套工作流 → 点确认后真的出图。**形态是可收起的画布浮窗**，
不是「agent 节点」：它管的是「把需求变成图」，图本身仍然是普通节点，和手建的一模一样。

> 完整设计（机制、工具集、刹车、失败回退、代码落点、分期）见 **《轻画-Agent设计文档.md》**。
> 这一节只记用户看得见的口径与验收。

> **2026-10-25 输入框与 @ chip**：Agent composer 使用 `--bg-surface`（浅色为白，深色为主题表面）。正文里的 @ chip 与正文同字号，按 `height:1.72em / padding:0 3px / margin:0 1px / radius:6px` 的紧凑规格显示；透明底 + 1px 描边，垂直居中。

| 用户看到什么 | 口径 |
| --- | --- |
| 入口 | 右下角可拖动彩色浮球；点击展开浮窗，收起后恢复浮球 |
| 浮窗 | 不占满屏，首次约为画布工作区高度的一半；可拖标题栏移动，可拖底部把手调整高度。位置与高度本机记忆 |
| 状态保持 | 收起只是隐藏浮窗，不卸载当前会话；再次展开时未发送正文仍在 |
| 多个对话 | 会话列表可新建 / 切换 / **改名 / 删除**；**每个会话记忆隔离**（切过去是另一套消息，不会串）。删除是两步确认，删完自动切到剩下那条 |
| 选模型 | 只列对话类模型；可把当前选中的设为默认（下次新会话用它） |
| 选技能 | 可不选；选了就把该技能正文当系统指令，按它的阶段来规划（§7A） |
| 给素材 | 拖图进对话窗 / 点「加素材」（**先落成画布节点**），或**在画布上选中节点后点「取选中」**（已在画布上，只记 id）；都记为可移除的标签，agent 靠节点 id 复用、不重复建 |
| 确认卡 | 改画布 / 花钱的动作**一律停下等确认**：先确认「要建的图」，再确认「真的去生成」。一次计划 = 一次撤销 |
| 收尾 | 落地后回读画布**逐条对账**（节点数 / 类型 / 连线端口 / 复用 / 有没有压住已有节点），结论回填给模型，由它给你收尾答复 |

> **2026-10-04 三条口径（用户拍板）**：
> ① **@ 里的模型只认前端清单** —— @ 菜单分「**节点 / 图片 / 视频**」三段，模型那两段走
> `presetModelsOf`（前端固定显示名），**渠道拉回来的名字一枚都不进**，也不含对话模型
> （「艾特按钮我要能图片模型和视频模型，就是前端的那几个，千万不要把渠道拉取的模型放上去」）。
> ② **模型面板的 ✓ = 「已经放进这次对话」** —— 勾选跟着正文里的 `model` chip 走（可以同时
> 亮好几枚，用来组「多个模型参与」的流程），**不是**「默认值」那两个字
> （「不是默认用这两个模型的意思，是把模型放在对话框中，意思是用这些模型进行生成，
> 能组成多个模型参与的流程」）。
> ③ **单步生成只建一个生成节点** —— 提示词直接写进生成节点的 `data.prompt`，
> `normalizeAgentPlan` 里另有一道确定性折叠，把模型照模板给的「提示词节点 → 生成节点」
> 合掉（一段提示词喂多个下游 / 目标自己已有正文 / 有一端在 `attach` 里，都不折）。
> ④ **正文的字段名只有一套**：提示词节点写 `data.text`，生成节点写 `data.prompt`。
> 真机数据里出现过「结构全对、正文落在 `data.prompt` 上」的写法 —— 画布上那个框是空的
> 却**不报错**，所以两头都堵：词表逐类型列出 data 字段，归一化再把写错的键搬回正位；
> 另外，**生成节点拿不到任何提示词的计划不许落地**（那种节点按定义永远跑不起来），
> 原因直接回给模型让它补上。
> ⑤ **参数的键名也只有一套**：比例是 `data.ratio`（**不是** `aspectRatio`），另外还有
> `resolution / quality / background / count / durationSec / videoMode …`。真机计划里
> 模型把比例写成了 `aspectRatio` ⇒ `ratio` 落回默认配方 ⇒ 用户说了 1:1、出图却是
> 1152×2048 的竖版。同样两头堵：词表把生成参数的键名逐个报出来（从写进节点数据的白名单
> 现取），归一化再把 `aspectRatio / aspect_ratio / aspect` 搬进 `data.ratio`。
> 另外：**技能面板点面板外的空白处也会收起**（原先只有再点一次按钮或按关闭钮两条路）。

> **2026-10-05 对话窗五条**：① 打开会话**不再凭空多出两枚模型 chip**（那是会话设置，
> 不是这句话要说出去的内容）；② **一个会话在跑，另一个照常能发**（运行态与中止控制器
> 都按会话各存一份，不再互相顶掉）；③ **发出去的引用保持矩形框**（用户消息按 chip 渲染，
> 与输入框长得一样）；④ **不再显示模型的中间叙述**（带工具调用那一轮的自言自语不落进
> 对话，只留收尾回复）；⑤ 头部那枚**「设为默认模型」撤掉**（按下当下没有任何可见变化）。
> 另：对话窗打开时右上角那排按钮（含日志）会让出来，不再被面板压住。

> **2026-10-22 三条生成边界**：① **没有可用生成渠道时 Agent 必须先说真实原因**：
> 图片 / 视频各自的可用性和缺渠道、缺令牌、缺模型等原因进入系统提示词，并在确认前再查一次；
> 不能把“没有运行记录”解释成渠道排队。② **自动生成是实时开关**：本轮运行中切到自动，
> 后续确认立即继续；已经停在确认卡时也会立刻接管。③ **批量保持全部并发**：每条生成
> 都是独立 API 请求，渠道支持并发，Agent 不擅自限流；用户说“剩下的全部生成”时一次覆盖
> 全部节点，并按节点逐项汇报成功 / 失败，不把部分成功说成全部完成。

> **2026-10-22 节点渠道不能静默改道**：用户在生成节点上确认的渠道是发送硬约束。
> 同一模型在别的渠道也声明了映射时，执行层不能按全局优先度把请求改到另一条渠道；
> 节点选中的渠道停用、无令牌或没有该模型时，应明确报出该渠道的阻塞原因。

> **2026-10-22 Agent 改模型与点击生成**：Agent 改模型时只提交前端模型名，渠道由系统
> 像创作面板一样自动反查；Agent 不得自行填写内部渠道 id。执行生成仍调用节点生成按钮
> 的同一套 `runNode`。4K 图片任务等待上限为 5 分钟，避免把上游排队误判成 120 秒超时。

> **2026-10-22 Agent 建好后直接跑**：节点建好且用户要出图时，Agent 直接对本次全部生成
> 节点调用一次 `runNode`，与用户逐个点节点「生成」按钮走同一执行链路；不先做单张试跑，
> 也不因第一张失败就暂停其余节点。

> **2026-10-22 A+ 详情页张数口径**：A+ 详情页的“快速优化项”是生成结构，不是纯提示词标签。
> 勾选几个合法优化项就生成几张；默认 4 项 = 4 张，全选 14 项 = 14 张。确认卡与实际任务
> 必须使用同一个张数，非法旧选项不计入。

> **2026-10-22 电商方案 AI 自审**：A+ 等流程化商品图不增加“先看方案再确认”的第二步。
> 用户仍只写要求并点一次生成；内部先用对话模型生成动态视觉系统与逐张方案，再把原图、
> 原始要求、已选模块和方案交给 AI 自审修正，检查文案、字体、网格、边距、对齐和跨图一致性。
> 自审通过后才创建节点并并发生图；自审失败停在付费生图前。确认卡要写明本次会多花一次
> 对话额度。

> **2026-10-30 长任务过程与直接下一步**：
> ① 任务计划卡固定在对话头下方，消息在自己的滚动区里滚动，不再把计划卡一起卷走。
> ② 模型请求有 SSE 时，折叠过程区实时接收供应商公开返回的 `reasoning_content / content`
> 和工具调用分片；收起时只显示最新一句，展开时保留完整累计正文。没有公开推理就不伪造。
> ③ 视觉验收可在 Agent 设置里单独选择“支持图片输入的对话模型”；默认快速验收最多看
> 4 张目标图和 4 张参考图，避免长任务把时间耗在非代表性图片上。
> ④ 输入“直接下一步 / 跳过验收”时，它是确定性控制命令，不是普通引导：先取消当前验收请求，
> 再把当前步骤标为完成、只启动下一步，并发送一条不显示成用户气泡的内部控制消息。
> ⑤ 流式请求一旦已经吐出任何内容，后续断线不得自动切换渠道重发，避免重复付费。

> **2026-10-05 画布两条**：① **`Ctrl / Cmd + G` = 把选中的节点打成一组**（按内容算框、
> 只收顶层节点、建组 + 归属合成**一步撤销**，完事选中新分组）；② **有素材的节点，
> 功能栏只留素材相关的动作**（提取选区 / 下载）—— 生成 / 重命名 / 复制 / 删除 / 关闭 /
> 渠道设置整排撤掉，唯一例外是正在生成时的「取消生成」。
> 另：对话窗的**会话选择器**也换成参数菜单那套 `ParamPicker`（原生 `<select>` 的展开层
> 由浏览器绘制，与旁边的参数菜单不像一家）。
>
> **2026-10-05 画布再两条**（第 9 / 10 条）：③ 那一栏补齐成
> **提取选区 · 宫格切分 · 下载 · 标注 · 旋转 · 预览**（多出来的四件见 §6.9 的表）；
> ④ 宫格切分与标注把产物落成**原图右侧的新节点**、旋转落成**复制出来的那个节点**。

#### 两条不能松的规则

| 规则 | 说明 |
| --- | --- |
| agent 建的节点与手建的**同源** | 新节点带默认配方（渠道 + 模型 + 生成参数），与 `createNodeWithDefaults` 走同一套解析。**漏了这条，建出来的生成节点点了「生成」不会有任何反应** —— 界面看不出异常，功能却是坏的（v1.0 漏过，v1.1 已补并加断言钉住） |
| 只用既有节点类型 | agent 不发明新节点；画布词表从 `nodeSpecs` 生成，加了节点类型它自动就会用 |
