## 1. 架构目标

### 1.1 要解决的问题

把所有交互逻辑、节点渲染、状态变更、持久化和网络请求堆在同一个页面组件里，会产生四种具体症状：

| 症状 | 成因 |
| --- | --- |
| 改一个节点类型碰坏另一个 | 6 类节点的渲染与交互共享同一处作用域 |
| 样式改动被旧规则覆盖 | 同类名多处定义，规则特异性不可控 |
| 撤销、保存、执行各写各的 | 数据变更入口不唯一，无法统一进事务 |
| 无法定位改动影响面 | 模块之间没有边界，改动范围只能靠人肉记忆 |

### 1.2 架构目标

1. **改动隔离**：新增或调整一个节点类型，只触及该类型的目录。
2. **单一变更入口**：图数据的每一次变更都经过命令层，撤销、持久化、执行由此自动获得一致行为。
3. **依赖单向且可机检**：分层依赖方向由工具强制，不靠自觉。
4. **纯逻辑可测**：坐标、拓扑、布局、打包、落位等规则是不依赖 UI 的纯函数，可单测覆盖。
5. **平台可替换**：网络、存储、凭据、文件通过端口接口访问。当前交付 Web 实现，测试用内存实现，后续接入桌面壳时业务代码零改动。
6. **扩展位前置**：新增节点类型、UI 打磨、画布内 Agent 三条演进路径在 M0 阶段预留接口（§5.7–§5.9），后续落地时只填实现。

### 1.3 设计边界

架构设计止步于「模块边界 + 契约 + 依赖检查规则」。模块内部的实现细节在实现过程中演进，架构文档只约束对外契约。
