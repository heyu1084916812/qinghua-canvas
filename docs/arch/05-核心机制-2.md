**应用壳契约**

| 项 | 口径 |
| --- | --- |
| 模块 | `app/AppShell.tsx`、`app/AppSidebar.tsx`、`app/sidebarState.ts` |

| 所有项目 | 侧栏展开态的完整项目树；一层文件夹内可混放画布 / 电商 / 漫剧，未归档按工作台分组；置顶项目独立置前 |

| 与画布关系 | 右侧工作区自适应缩小；画布仍以 `[data-canvas-surface]` 的真实矩形计算坐标与命中 |
| 与页面的关系 | 页面不再绘制自己的全局顶栏；页面内可有自己的区头 / 工具区，但不能提供重复的一级导航 |

**应用壳依赖约束**

- `app/AppShell` 可以 import `react-router-dom`、`ui/` 与共享的只读数据端口；
- **不得 import `workbenches/canvas/*`**；画布内入口通过路由 / 事件与 `pages/CanvasPage` 通信；
- `pages/*` 不得反向 import `app/AppShell`；页面通过路由在壳中渲染；
- `AppShell` 不属于 `pages` 或 `workbenches`，避免任何一层把它当业务页面或工作台。

**store 工厂化**

`createStore` 接受 `WorkbenchId` 与工作台私有切片，每个工作台页面挂载时调用一次。共享切片自动注入；私有切片随路由进入而创建、随路由离开而销毁。命令按工作台注册，跨工作台不共用（`CanvasCommand ∪ ComicCommand` 是工作台注册表层的并集，不是全局联合类型）。

**兑现状态（M5 已落地）**：上表除 `features/comic/` 之外均已实现并经冒烟验证。补充两条实践结论：

1. **共享契约要泛型化**：`AppStore.dispatch(cmd: Command)` 原先硬编码画布的命令联合，是隐藏的跨工作台耦合点。M5 改为 `AppStore<TSnapshot, TCommand>`（当时默认值保持画布语义，既有调用方零改动），`createStore` 按 `workbench` 重载返回类型，调用方不再需要手写类型断言。**M6-1 追加更正**：那两个默认值本身让共享层反向依赖了画布私有类型（`GraphSnapshot` / `Command`），已改为**两参必填**、各工作台显式传入（`CanvasStore extends AppStore<GraphSnapshot, Command>`），由 `no-shared-to-workbench` 规则锁定。新增工作台时只加一个 case，共享接口不动。
2. **路由级 lazy 需要 SSR 冒烟相应适配**：`renderToString` 不会等待 `React.lazy`，只会输出 Suspense fallback。整树渲染冒烟改用 `renderToReadableStream` + `await stream.allReady`（Web Streams 版，避免引入 `@types/node`）。

**轻量的真实含义**

不为"未来加工作台"预建插件系统、依赖注入容器或 monorepo 工作台包——那比画布本身还重。现在的做法是：

1. 目录并列（物理隔离）
2. store 工厂（生命周期隔离）
3. lint 规则（编译期隔离）
4. 路由级 lazy（包体积隔离）

四条加起来 ~半天 M0 成本，做完后第二个工作台的落地成本仅与它自身代码量成正比。

### 5.11 多端口节点 · ✅ 已实现（2026-09-29）

**问题**：到此为止，「端点」一直是**一对布尔**（`ports: { input, output }`），位置写死在
左中 / 右中。这对前七个节点类型都成立，唯独装不下融合节点（§6.23）：它右侧要同时有
**局部修改图的入口**与**融合结果的出口**。

**做法：把端点从布尔升级成声明**（`domain/canvas/nodeSpecs/ports.ts`）。

| 概念 | 契约 |
| --- | --- |
| `PortDecl` | `{ id, kind: 'input' \| 'output' \| 'both', side: 'left' \| 'right', y: 0–1, label?, multi? }`。`'both'` = **同一个锚点既是入也是出**（融合节点右口）：从它往外拖 = 出，上游落在节点那一侧 = 入。`multi` 只对入方向生效 |
| `NodePorts` | `{ input: boolean; output: boolean; extras?: PortDecl[] }` —— 默认那对仍用布尔写法，老节点规格**一个字都不用改** |
| `portDeclsOf` | 展开成完整清单（`input` → `output` → `extras`），DOM 顺序与它一致 ⇒「同侧多口谁在上」可预测 |
| `portDeclOf` | 按 id 取声明；取不到返回 `null` ⇒ 调用方据此拒连线 / 不画锚点 |

**id 沿用历史值**：默认口就是 `input` / `output`（**不是** `original` / `result`）。
冒烟与既有断言都按 `[data-port="input"]` 定位，改名等于把它们全部改红 —— 而那不是
这次要动的东西。融合节点的第三只口 id 是 `patch`。

**连线侧的三处同步**（漏任何一处都会静默错位）：

1. `Edge` 补 `sourcePort` / `targetPort`（**可选**，缺省即历史口径 ⇒ 老数据零迁移）；
   去重键从 `(source,target)` 改成 `(source,sourcePort,target,targetPort)`，
   并给声明了 `multi: true` 的口放行同源多边（`patch` 是唯一一个）。
2. `canConnect` **按 id 解析端点**再判存在性与方向，而不是看 `ports.output` 布尔 ——
   `patch` 在右侧但语义是**输入**，只看「左入右出」会把它判反。
3. 描点位置由声明给出（`side` + 纵向比例）而不是写死中点；曲线控制臂对
   **逆向端点**（长在右边缘的入口）收短，否则线会甩出一个绕出节点的大回环。

**拖线落点怎么选口**：松手只给出「一个节点」，而节点可能有两只输入口，
故按**离指针最近的那只输入口**判定（`nearestInputPort`，纯函数）。
只有一只候选时就是它 —— 与历史行为完全一致。

**接线清单里新增的一条**：新类型若产出**图片**，要逐个补各下游的
`accepts.upstream`。这类「少一个」**读代码发现不了**（表现为「线连不上、也不报错」），
只能靠清单逐项过。

### 5.12 Agent 应用壳面板与现有推理循环 · ✅ 已实现

画布 Agent 由壳层宿主、现有 `agentLoop`、编排控制器和宿主端口组成，不引入外部
Agent/Harness runtime：

```text
app/AgentHostOutlet（通用 outlet + opaque host registry）
  -> canvas 模块注册 CanvasAgentHostRenderer
       -> CanvasStoreProvider（项目缓存 store）
       -> CanvasExecutionValueProvider（稳定 live API adapter）
            -> AgentDock / AgentPanel
            -> AgentController
            -> canvas/agent/agentLoop（现有推理与工具循环）
            -> ToolRegistry -> CanvasToolBridge / HostServiceBridge
            -> ModelRoutePort -> 现有 RouteResolver / RouteExecution
            -> MemoryPort -> ContextBundle / contextMemories
            -> SessionEventAdapter -> agentSessions / agentJobs / agentEvents
```

**依赖方向**

| 模块 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| `app/AgentHostOutlet` / registry | `AppShell` 布局、opaque record、renderer kind | 画布 store、画布节点实现、外部 Agent 包类型 |
| `CanvasPage / CanvasAgentHostBridge` | 路由、项目 store / execution descriptor、active owner | 让 `AppShell` 反向 import 工作台 |
| `CanvasAgentHostRenderer` | 已捕获的 store / live execution adapter、现有 Agent 组件 | 重新挂执行引擎、复制 AgentLoop |
| `AgentController` | Agent 领域、Agent 状态端口、ToolRegistry / Route / Memory 端口 | DOM、React 视图、渠道适配器、Workbench store |
| `agentLoop` | 当前 Agent 会话、公开过程事件、工具调用协议 | 直接写画布 store、直接发渠道 HTTP、第二套计费 |
| `ToolRegistry` | 工具 schema、权限和桥接接口 | 未登记工具、任意 shell / 文件系统 |
| `ModelRoutePort` | 现有 `ChannelStore` / `RoutePlan` / `RouteExecution` | 第二套 provider 或第二次 retry |

**常驻宿主边界**

`CanvasPage` 只在挂载期间发布 `CanvasAgentHostPayload`（projectId + 缓存 store + execution adapter）并把
对应 host 设为 active/owner；卸载时只 deactivate，不 remove。`AgentHostOutlet` 对所有 record 保持 renderer
挂载，非 active record 仅 `display:none`。`AgentDock` 的 panel 仍留在 AppShell slot 的 React 子树里，通过
`hidden` 保留 DOM；只有 owner 能写 `data-agent-shell-active` / width / resize，非画布路由必须让 slot 回到
宽 0。

每个项目的执行真相由 `features/shared/execution/executionRuntime.ts` 与
`workbenches/canvas/execution/canvasExecutionRuntime.ts` 持有：controller registry、running plans、
task→node、取消索引和 version baseline 都在项目 runtime。`createCanvasExecutionHostAdapter()` 捕获仍存活的
`runNode / runGroup / cancel / completeText / appendRecord` 闭包，但 `nodeStates / nodeStateOf / isRunning`
每次读取 live store，不能把 render 快照冻给常驻 host。共享 `taskLifecycle` 先把 runtime 标成 closing，
再 abort，并把完整 Promise 放进 in-flight registry；execution engine 与画布 operations 两者都等待。
AgentPanel 的 send / confirm / continue / cancel / stop、queue enqueue/remove/edit/claim/finish/pump、
Session create/rename/delete/patch、任务计划、引导、附件/技能/收藏、sticky 模型写同样受项目 closing
registry 约束；draft / composer 同步写用 `runSync`，所有 fire-and-forget Promise 必须注册并 catch。

项目删除改为两阶段：`prepareProjectRuntimes` 先同步阻断所有入口并等待 idle，仓储成功后
`commit` 才 finalize runtime、移除 host 并 purge；仓储失败则 `rollback`。`commit()` 返回
`{ status: 'cleanup_complete' }` 或 `{ status: 'cleanup_failed', error }`，不能再用 boolean 把
“仓储成功”和“runtime 清理成功”混成一个事实。cleanup 失败时 registration、项目锁与未完成的 finalize
状态都保留；`ProjectRuntimeCleanupError.workCommitted=true / retryable=true`。同一 projectId 集合再次
调用 `withPreparedProjectRuntimes` 时只重试 cleanup 并返回先前 work 结果，不重复删除仓储数据。
prepare 或 rollback 的恢复失败走另一条状态链：`recovering / recovery_failed`，对应
`ProjectRuntimeRecoveryError.workCommitted=false`。恢复失败同样保留锁与 registration，但不会伪装成
cleanup；底层 barrier 后来 idle 时，重试或再次删除会先重新 open，再执行新的 prepare 与仓储 work。
`rollback()` 返回 `rolled_back / recovery_pending`，普通 work 失败且 rollback 成功时仍只抛原 work 错误。
调用先一次性 claim
全部 projectId：任一项目已有操作时整体抛 `ProjectRuntimeBusyError`，不能部分持锁。claim 持续到
commit，或 rollback 后全部 participant 真正 idle 并重开；期间同 project/key 注册只能复用旧
generation，不同 key 也立即纳入同一 shutdown。commit 循环吸收迟到注册后再 finalize，保证不留下
第二个 host/runtime。每个 prepared control 记录真实 `idle / finalized / lastError`；prepare、recovery
和 commit 的等待都受统一 shutdown timeout 约束。late runtime resolve 后才允许 finalize；reject 或
超时直接进入 cleanup_failed，不 finalize、不删注册、不释放锁，之后再调用同一 disposal 仍可重试。
TaskLifecycle 的
`open / draining / closed` 区分“尚未 idle”与“最终关闭”：有在途 Promise 时不允许假装重开；idle 后
flush 或仓储失败可恢复同一 host；超时则在真实 idle 后自动恢复。runtime tombstone 阻止旧 runNode 闭包
和生成入口复活已关闭代际；合法 CanvasPage 激活才建立新代际。`AgentHostRegistry` 与
`ProjectRuntimeRegistry` 的记录都带 generation：HMR dispose 先同步失效旧代际，再异步等待旧 disposer；
移除时只删除仍指向 capture token 的那条记录。StrictMode cleanup 只 deactivate，不会把常驻 host 提前删掉。

`ProjectRuntimeRegistry` 对外暴露可订阅的 pending 快照：operationId、projectIds、status、
workCommitted、retryable、workReason、recoveryReason。AppShell 常驻渲染
`ProjectRuntimeRecoveryNotice`，所以项目页或侧栏卸载后仍能重试。页面局部按钮也只保存 operationId，
实际状态与 projectIds 从快照读取。`retryProjectRuntimeCleanup(projectIds)` 只接受完整集合；子集、
混合集合或包含其他 active operation 时抛 `ProjectRuntimeRetryScopeError`，完全不相关集合才 no-op。
`committing` 也进入快照但 `retryable=false`，全局与页面按钮统一显示“清理中…”。`commitOperation()` 只允许
从 `prepared / cleanup_failed / 同一 commitPromise 的 committing` 继续；`preparing / recovering /
recovery_failed` 抛 `ProjectRuntimeCommitStateError`，不得先写 `workCommitted=true`。并发调用返回同一
Promise，finalize / release / 注册移除只执行一次。

cleanup 全部成功且 `workCommitted=true` 后，registry 才发出 `ProjectRuntimeCompletion`。AppShell 单点订阅，
并用最新 pathname 调 `finalizeCommittedProjectRuntimes`：清 activeCanvas、两类 handoff、canvas store，
仅当当前路由仍是该被删画布时 `replace('/projects')`。页面局部和全局入口都只重试 registry，不再各自
清内存或导航。`workCommitted=false` 的 recovery 成功不发 completion；HMR 的 runtime-only dispose 也以
`markWorkCommitted=false` 提交，避免误清仍存在的项目。

shutdown 开始后 `AgentHostRegistry` 冻结该 host generation。`upsertAgentHost()` 在冻结期间只能更新 payload，
不能换 generation；HMR 也不递增冻结记录。若多 participant 中部分 finalize 已成功、另一个失败，冻结保持到
整个项目操作成功；此时重挂载会得到“不落表”的冻结句柄，不会留下新 host。整体 commit 成功后才调用
`releaseFinalized()` 释放冻结；rollback 的 `reopenIfIdle()` 也会释放冻结，使后续合法页面激活可以建立新代际。
StrictMode 仍只 deactivate，不触发冻结。

`combineTaskShutdownControls` 为每个 child 维护单独的 finalized / released 位。`canFinalize()` 只看尚未
完成的 child；`finalize()` 只调用它们。Canvas host 已成功而 execution finalize 返回 false / 抛错时，外层
项目操作进入 cleanup_failed，第二次 commit 只重试 execution。全部 child 成功后才调用
`releaseFinalized()`；它逐个 release 未完成项并逐项记账，某一项抛错也进入 cleanup_failed，重试跳过已释放项。
`ProjectRuntimeRegistry` 的 prepared runtime 使用同一 released 契约，保证部分成功后不会重复释放。

AgentPanel 的 `createAgentPanelShutdownControl()` 把 lifecycle `whenIdle()` 与最终 `store.flush()`
合成同一个 Promise；`waitForIdle()` 的 timeout 从关闭开始覆盖“在途任务收口 + flush”整段。flush
pending 时 `canReopen / canFinalize` 都返回 false，timeout 只结束本次等待、不取消屏障。flush
resolve/reject 且 barrier 结算后才允许 rollback 重开或 commit finalize。

loopDeps 跑模型与自动确认；路由失败或抛错时显示原因，按原 origin 把 Job 转 failed 并标记

- 工具效果按 `(jobId, stepId, toolCallId)` 去重，付费请求按
  `(operationId, runPlanId, taskId, attempt)` 去重。
- 页面重开只恢复未提交规划与可查询任务；结果不明进入 `needs_attention`，不允许通过
  “重试”静默再付一次。

**写操作执行前检查与版本保护（2026-11-23，#1187–#1189）**

- 工具确认前统一经过 `precheck`：运行类工具继续做现有 `runNode / runFrom` 预检；
  写画布类工具由 `prepareMutationCall()` 解析真实目标，目标不存在、连线不存在或批量步骤
  自相矛盾时直接拒绝，不弹确认卡。
- 可执行请求会把一个隐藏的 `qinghua.mutation.v1` 前置条件写回确认参数，记录画布语义版本
  以及每个目标节点 / 连线的状态摘要。用户确认后、真正 dispatch 前由
  `verifyMutationPrecondition()` 再比一次；目标在这段时间被删除、替换或修改时不覆盖用户刚改
  的内容，而是要求重新读取画布。
- `CanvasStore.getRevision()` 只统计图语义变化，选中、视口、菜单等瞬态不计入。这里的保护
  按目标摘要比较，不会因为用户移动了无关节点而误拦。
- `renameNode` 只改 `node.rename` 的标题，不再借用 `updateNode` 修改生成参数。
  `applyCanvasBatch` 一次最多 20 步，支持已有节点的改名、平移、断线和删除；整批先校验，
  再放入同一个 `multi-step` 事务，成功后一次 Undo 可全部回退，中途异常也按整批回滚。
- 每次进入工具账本后，完成结果自动附稳定 `requestId`；pending、failed、conflict 文案也带同一
  编号。超时或重启后，`readOperation` 只按 `requestId` 查原 Job 的不可变工具事件，不调用
  工具执行器，因此不会重新写画布或重复提交已计费请求。

**Agent 电商 Skill、锚点与调研门禁（2026-11-26，#1208–#1215）**

- 本轮无显式 skill chip 时，`chooseAgentSkillsForTurn()` 只读正文与用户技能元数据做确定性匹配；
  显式 chip 优先，纯画布操作不自动加载技能。自动命中必须在过程区显示真实技能名。

  `applyPlan` 前 `guardGenerationPlan()` 统一比例并检查电商共享锚点、文字层级；显式参考失败时
  `blockedIds` 必须在同一入口拒绝 `applyPlan / runNode / runFrom`。
- 图片调研 `imageMaxResults` 默认 100、范围 100–120；电商查询自动补中文平台、主图排版、
  详情页卖点与英文商品图角度。结果投影保留 `searchQueries` 与 `siteStatuses`，对话状态面板展示
  目标 / 实收和每站原因，不得静默截断。
- 问题卡可见正文固定按真实题数生成；工具未返回结果前，`runNode / runFrom` 只能显示等待确认文案。
