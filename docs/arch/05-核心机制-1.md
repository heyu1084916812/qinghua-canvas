## 5. 核心机制

### 5.1 节点注册表 · ✅ 已实现

> **两条几何规则落在 domain（2026-09-19）**，理由是它们都有「写错也不报错」的性质，
> 必须能被单测钉住，且都要被**再渲染**复用：
>
> - `geometry/portMagnet.ts`：端点吸附。位移方向必须「圆心 → 指针」（取反变成躲开指针）、
>   吸附量必须随距离衰减（否则端点会跳出节点边框）。UI 只负责把结果写进 `transform`；
>   判定用**几何距离**而非 DOM `:hover`——端点隐形时仍可命中，会出现「看不见却已生效」。
> - `layout/arrangeModes.ts`：宫格 / 水平 / 垂直排列。与 `layout/align.ts` **刻意分开**：
>   排列**两个方向一起改**（重排成网格 / 行列），锚点为「包围盒中心不动」，避免排一次就甩走整组。
>   （`layout/align.ts` 已于 2026-09-19 随「8 种对齐」一起下线：其「拉齐边缘」的能力
>   被排列与整理覆盖，三者并存只会让工具栏语义重叠。）
>
> **面板的可交互性是一条容易被忽略的契约**：浮层由 hover 驱动时，按钮与浮层之间
> 必须留一条不可见的延伸区、并在离开后**延迟**关闭。少了任一条，指针从按钮移向浮层
> 的途中（两点间有 8px 空隙）就会触发关闭——表现是「面板一闪、根本点不中」。
> 这类缺陷在单测里看不出来（DOM 都在），只有真机指针轨迹能暴露。

新增一个节点类型的完整动作：

1. 在 `domain/canvas/model/node.ts` 的 `NodeType` 联合类型里加一个字面量
2. 在 `domain/canvas/nodeSpecs/<name>.ts` 写 `NodeSpec`（行为：`sizing` / `accepts` / `createDefaultData` / `collectInputs`，可生成的再加 `generate` 或 `toRunRequest`）
3. 在 `domain/canvas/nodeSpecs/index.ts` 调用一次 `registerSpec(...)`
4. 新建 `workbenches/canvas/nodes/<name>/` 目录，写 `View` 与可选 `Panel`
5. 在 `workbenches/canvas/nodes/index.ts` 调用一次 `registerView(...)`

**共 4 个文件**（1 个类型联合 + 2 个注册 + 1 个 spec/视图目录），不改命令层、不改执行层、不改右键菜单与工具栏。

### 5.2 命令、事务与持久化 · ✅ 已实现

```
视图 / 交互控制器
      │  emit(event) / dispatch(command)
      ▼
命令处理器（state/commands/*）
      │  读取 domain 规则做校验
      ▼
CommandResult { patches, inverse, transaction, persist }
      │
      ├──▶ graphSlice 应用 patches（渲染）
      ├──▶ history 按 transaction 入栈 inverse（撤销）
      └──▶ persistenceService 按 persist 计划 800ms 防抖写入
```

一次用户操作 = 一个事务。拖动这类连续操作用 `coalesce` 模式合并，从按下到松开只产生一个撤销步骤与一次持久化事务。

**例外：`assets` 表插队，不等防抖。** 节点拿到 `assetHash` 的那一刻 UI 就要按 hash 通过 `PlatformProvider → StoragePort` 去本机 shared-store 读字节（内存里没有第二份），素材若跟着 800ms 防抖走就有一段固定空窗——上传完先看到空白节点；多张连传时主线程被哈希 / 解码占住，防抖计时器一并推迟，空窗会长到「看起来没传上去」。素材是**内容寻址的幂等 upsert**（id = 内容哈希），提前写没有副作用，故让它插队；其余表仍走防抖（拖动节点每帧一次 `node.move`，逐次落库才是真的卡）。冲刷改为**串行链**，插队不会与后续写入交错丢写。旧 IndexedDB 只承担迁移读取，不是当前 `useAsset` 的权威来源。（M6-26 / 0.1.17 校正）

**素材库与内容仓库分层（2026-09-29）。** `assets` 只回答“这份字节是什么、在哪儿”，`assetLibrary` 才回答“用户主动收藏了哪张、当时的生成信息是什么”。`/assets` 只查 `assetLibrary`；取消收藏只删收藏关系，绝不动 `assets` 字节或画布节点。收藏行是保存当时的冻结快照，节点后续改提示词 / 模型不会回写它。这样“内容寻址仓库”和“用户收藏列表”各自只有一条清晰语义，也避免清理收藏时把别的节点正在引用的字节删掉。

**节点显示走缩略图，原图只给灯箱 / 旋转 / 标注（2026-10-05，对账 #231）。**
`useAsset` 拿的是 `assets` 行里的**全分辨率字节**，而画布节点只显示约 240×192 ——
浏览器仍然按**原图**解码：3840×2160 一张解码后 ≈ 33MB（宽 × 高 × 4），可见几十张就是 GB 级内存
（#195 那次崩溃里「应用侧放大」就是这一层）。现在明确分两条路：
`useAssetMeta` = **原图**（灯箱 —— 含它里面那两种模式：**旋转与镜像** / **标注**，那些地方要的是像素）；
`useAssetThumb`（含 `useAsset`）= **一切"小尺寸显示"**：画布节点本体（生成 / 对比 / 融合 / 循环的媒体框）、
面板里的素材条、**日志面板里一排排历史产物**、@ 提及的小图。判断标准是**显示尺寸**，
不是"在哪块 UI 上"；只有要读像素的地方（灯箱，含它里面的旋转 / 标注模式）才用 `useAssetMeta`。

⚠️ 这条口径最初被一条断言挡过：日志面板那条「实际像素与产物真实像素一致」原来拿 `img.naturalWidth` 当证据，
而缩略图会让它变成 640。**改的是断言**——现在从**库里的字节读 PNG 文件头**（与界面那行文字是两个独立来源，
交叉验证更硬），而不是把面板的小图能力砍掉（对账 #235）。

缩略图三条口径：① **生成一次就落库**（`assets.thumb`，WebP，最长边 640），不进内存 LRU ——
存下来之后每次打开项目都直接命中，不必每开一次项目把几十张图重新解码 + 重编码；
② **本来就小就不动它**（原图最长边 ≤ 640 直接用原图：省一次重编码，也省一份重复字节），
尺寸读不出来时也不猜（宁可继续用原图）；③ 生成走**限流槽**（同时最多 2 张）——
「一屏几十个节点同时挂载」正好就是我们要修的那件事，背景任务不该把前台再压垮。

真机实测（`scripts/probe-node-thumb.mjs`，量的是 `img.naturalWidth` = 浏览器真正解码出来的像素宽）：
3000×2000（解码 23MB）⇒ 首访后台落库一张 **1056 字节**的缩略图 ⇒ 再访解码 **640×427（1.0MB）**。
**谁负责生成**（同日补齐，对账 #232）——两条路，覆盖所有素材：

| 素材来源 | 谁补 | 时机 |
| --- | --- | --- |
| **新素材**（用户导入 / 模型产物） | store 的 `writeOnce` —— **素材行的唯一落库出口**，落库成功后顺手补一张（`void`，不 await） | 就在落库那一刻：不用先"看"它一眼 |
| **存量素材**（这次改动之前就在库里的） | `ThumbBackfill`（挂在应用壳上、**无界面**）：在**非画布页面**跑一趟，补完在 `presets` 留一行 `job:assetThumbBackfill` 标记 | 打开应用、停在项目页时；**一进画布立刻中断**，且**不打标记**（下次接着补） |

那行标记为什么够用：**新素材不依赖它**（落库时就补好了），所以"全库扫一遍"这辈子只做一次 ——
而这件事必须避免重复（`assets` 每行都带字节，每次启动都重扫不可接受）。

真机实测 `scripts/probe-thumb-backfill.mjs`：3 张 3000×2000 的"老素材"（无缩略图）⇒ 各补一张约 1KB 的缩略图并打上标记；
再塞 60 张、跑到一半就进画布 ⇒ **中断且没有打标记**（下次继续）。
⚠️ 顺带更新了 G55 的一条断言：它原来钉的是「`createImageBitmap` 一次都没被调用」，而缩略图生成**必然**要解码 ——
现在改成分开数：**不带 resize 选项**的那次才代表"取尺寸走了解码"（必须为 0）。
### 5.3 坐标系统 · ✅ 已实现

三套坐标，边界由 `domain/geometry` 统一换算：

| 坐标 | 用途 | 存储位置 |
| --- | --- | --- |
| world | 画布全局坐标，节点持久化值 | `nodes.x / y`（`parentId` 为空） |
| local | 容器内相对坐标 | `nodes.x / y`（有 `parentId`） |
| screen | 屏幕像素，随视口变换 | 不持久化 |

容器移动只更新容器自身的 world 坐标，子节点的 local 坐标不变，因此拖动容器不会重写全部子节点。跨越容器边界时由 `convertOnReparent` 一次性换算。

**归属的唯一真源 = `nodes.parentId`（2026-09-17 收敛）**

| 数据 | 角色 | 规则 |
| --- | --- | --- |
| `nodes.parentId` | **真源**：决定归属与坐标系 | 子节点的 `parentId` = 容器节点 id（分组 / 批量），坐标是相对容器的 local |
| `nodes.data.childIds` | 仅用于 `group` / `batch` 两种收纳型容器 | 决定组内顺序（§6.11 / §6.12 的 3×3 排序依据） |

> **结果组已整体下线**（用户 2026-09-17）。此前它是「归属的第二真源」——
> 与 `parentId` 必须保持一致、不一致时要重建并写诊断日志，本身就是一处持续成本。
> 连带删除：`resultGroups` 表与三张视图、`ResultGroupLayer`、`resultGroupLayout`、
> `layoutResultGroup` / `resultGroupCells`、`canConnect` 里「组不作端点」的两条规则、
> `coords.toWorldRectInGraph` 的「父级可能是组」分支、导入导出里的结果组行，
> 以及 `.flow.json` 的 `resultGroups` 字段（降为可选：导出不写、导入忽略）。
>
> 产物改由**每次调用各落一个承载节点**表达（§5.5 落位），于是「组内统一格位」
> 这套口径不再需要——节点一律按产物真实比例呈现。
>
> **数据库迁移**：Dexie **v1 保留 `resultGroups` 定义**（已存在的库是按 v1 建的，
> 从 v1 删会让它 schema 不匹配而打不开），**v2 不列出该表** ⇒ 升级时删除。
> 于是「老库能打开、升级后表消失」。v2 同时新增 `presets` 表（见下）。

### 5.4 渲染管线 · ✅ 已实现

```
FlowSurface（React Flow 的视口受控；视口 transform 由 RF 自己管）
  ├── FlowEdge          自定义边：老锚点 + 加宽命中区 + 删除按钮
  ├── FlowNode          自定义节点 → NodeFrame → NodeSpec.View
  │                     （容器子节点由容器 View 按网格渲染，不是 RF 节点）
  ├── FlowPortLayer     端点命中层：在**所有节点之上**收拖线手势（RF 的 Handle 只留几何 / 冒烟锚点）
  ├── FlowDraftLayer    拖线草稿（屏幕坐标，画在节点下面）
  └── 浮层              HUD / 小地图 / 跟随栏 / 多选栏 / 面板 / 菜单（只读 store，自成一体）
```

- **视口受控**：`flow/viewportBridge.ts` 双向换算（轻画 `viewport.x/y` 是**世界坐标**语义、RF 是**屏幕像素**位移 —— 同名不同义）
- **平移 / 缩放只改 RF 视口容器那一个 transform** ⇒ 节点子树不参与拖动（这就是"节点里带图也不卡"的来源）
- **端点手势统一收口**在 `FlowPortLayer` → `useEdgeDrag`（两个引擎共用的那套建边语义）；
  RF 的 `Handle` 只提供端点几何与冒烟锚点 —— 别给它接手势（它会被相邻节点整块盖住，实测重叠 17px 就拖不出线）
- 指针移动处理统一经 `rafThrottle` 合帧

### 5.5 执行引擎 · ✅ 已实现

`features/execution` 分三段，全部可脱离 React 测试：

```ts
// features/canvas/execution/buildRunPlan.ts（纯函数）
// scope = 'node' 时传 originNodeId；global 全图运行不传 originNodeId
export function buildRunPlan(
  scope: RunScope,
  origin: { originNodeId: string } | { subgraph: GraphSnapshot },
  graph: GraphSnapshot,
  // 入参含 'single-alt'：函数内部解析为 executionMode + newDownstream，不把 single-alt 传下去
  mode: Exclude<RunMode, 'idle'>,
  // refreshStale 模式必填：只有落在 staleNodeIds 里的节点才入 plan
  // 其余模式传空集合即可，不参与过滤
  staleNodeIds?: ReadonlySet<string>
): RunPlan

// single-alt 解析规则（本次修订）：
//   mode === 'single-alt'  →  executionMode = 'single'，newDownstream = true
//   其余                   →  executionMode = mode，newDownstream = false
// newDownstream = true 时，结果不复用已有槽位，改由 slotPlacement 在拓扑方向铺新下游节点
// （命名「原节点名的输出N」），旧节点与旧内容完全不动。见产品文档 §6.19.3 / §6.19.4。

export interface RunPlan<TTask extends RunTask = RunTask> {
  id: string                          // runPlanId，用于 runPlan.execute / runPlan.cancel / multi-step 事务绑定
  tasks: TTask[]                      // 已拓扑排序的执行单元
  scope: RunScope
  mode: Exclude<RunMode, 'idle' | 'single-alt'>
  /** Alt+R：保留旧内容，结果铺到新下游节点而非复用空槽位 */
  newDownstream: boolean
}

// 【M6-5 泛型化】RunTask 收窄为工作台中性的基类（id/nodeId/request/dependsOn/fingerprint/
// params/collectionItemId?/seq?）；画布扩展 CanvasRunTask（补 slot: SlotPlan、params: NodeData），
// comic 直接用基类（一格 = 一 task）。见 domain/shared/execution/plan.ts。
export interface RunTask {
  id: string
  nodeId: string
  request: RunRequest
  dependsOn: string[]                 // 前置 RunTask id（拓扑序来源）
  fingerprint: string
  params: unknown                     // 各工作台自定（画布 NodeData / comic ComicPanelParams）
  collectionItemId?: string | null
  seq?: number
  // 入 plan 的筛选口径（由 buildRunPlan 决定，任务本身不感知）：
  // refreshStale 模式：仅当 origin 节点或其下游为 stale 时才入 plan
  // rerun 模式：从 origin 开始的所有下游全部入 plan
  // rerunAll 模式：忽略 staleness，全图所有可执行节点全部入 plan
}

// 校验：环 / 模型缺失 / 渠道缺失 / 空批量 / 两个批量维度
// 展开：批量集合笛卡尔展开
// 排序：scope = node → 单节点；global → 全图拓扑序
// 落位：单点生成走 domain/canvas/layout/slotPlacement（BFS 空槽位，见产品文档 §6.19.3）；
//       拓扑生成（rerun / refreshStale / rerunAll）按拓扑序覆盖式重跑，不查空槽位；
//       newDownstream = true（Alt+R）走 slotPlacement 的「铺新下游」分支
```

```ts
// features/shared/execution/runEngine.ts（副作用）
// 【M6-1 更正】原设计置于 features/shared/execution/（认为「与工作台无关」），但实现中
// 落位/写回硬编码了画布命令（node.create / resultGroup.create / generationSpec / RESULT_CELL），
// 实际是画布专用，故先归位 features/canvas/。
// 【M6-5 兑付】待 comic 作为第二个消费者出现后，按 §5.5 路径 B 把落位/写回抽成
// **注入式 ExecutionPlacement**（begin/commit/shouldCollect/record/finalize），引擎本体
// 泛型化 `runEngine<TTask, TCommand>` 并搬回 features/shared/execution/；画布专有落位在
// features/canvas/execution/canvasPlacement.ts、comic 在 features/comic/execution/comicPlacement.ts。
// 从此引擎不认识任何工作台命令——文档意图（共享）与实现（共享）一致。
// 关键设计：runEngine 不依赖 dispatch。调用方（装配层）通过 writeBack 注入「如何把图变更落回 store」
// 这样 runEngine 可独立单测（喂入 mock writeBack + mock placement），不污染上层
export interface RunEngineDeps<TTask extends RunTask, TCommand> {
  // runPlan-level 取消信号——一次拓扑生成的整次活动一个 AbortController
  // 取消时：已成功的 RunTask 保留结果写回；未启动的跳过；正在跑的终止
  signal: AbortSignal
  // runEngine 把图变更以「TCommand 序列」形式提交，由调用方决定怎么落回 store
  // 通常实现：writeBack(commands, tx) => commands.forEach(c => dispatch(c, tx))
  //
  // transaction 参数由 runEngine 传入而非调用方注入：runEngine 知道 planId 与调用次序，
  // 整次 plan 的第一次 writeBack 调用传 { mode: 'multi-step', planId, label }，
  // 后续调用不传，同 planId 的 Command 自动合并到同一 undo 栈项。
  // 这样「哪些 Command 属于同一次拓扑生成」这件事只有 runEngine 一处知道，不会散落到调用方。
  writeBack: (commands: TCommand[], transaction?: TransactionBoundary) => void
  channelResolver: (request: RunRequest) => ChannelAdapter
  /** 落位 / 写回适配器（M6-5 路径 B）：把产物翻译成工作台自己的命令 */
  placement: ExecutionPlacement<TTask, TCommand>
  policy: {
    maxRetries: number                // 默认 2（共 3 次尝试）
    backoffBase: number               // 默认 1000ms
    retryableStatuses: number[]       // 默认 [408, 429, 5xx]
  }
  onTaskUpdate?: (taskId: string, state: RunTaskState) => void
}

export type RunTaskState =
  | { kind: 'queued' }
  | { kind: 'running'; startedAt: number }
  | { kind: 'succeeded'; result: GeneratedAsset[]; duration: number }
  | { kind: 'failed'; error: AppError; attempts: number }
  | { kind: 'canceled' }

export interface RunSummary {
  runPlanId: string
  mode: Exclude<RunMode, 'idle' | 'single-alt'>
  // 各任务的终态
  taskResults: { taskId: string; nodeId: string; state: RunTaskState }[]
  succeeded: number
  failed: number
  canceled: number
  startedAt: number
  finishedAt: number
  /** 本次执行产出的 RunRecord（成功 / 失败 / 取消各一条），由调用方落库 */
  records: RunRecord[]
}

export async function runEngine<TTask extends RunTask, TCommand>(
  plan: RunPlan<TTask>,
  deps: RunEngineDeps<TTask, TCommand>,
): Promise<RunSummary>
```

```ts
// features/shared/execution/placement.ts（M6-5 路径 B · 落位适配器接口）
// 引擎与工作台之间的唯一接缝：引擎问「怎么落」，工作台答。
export interface ExecutionPlacement<TTask extends RunTask, TCommand> {
  /** 任务开始前：给出落点 targetId，并返回需要写入的预备命令（画布：建/复用承载节点） */
  begin(task: TTask, opts: { isRepeat: boolean }): { targetId: string; commands: TCommand[] }
  /** 成功产出：把产物挂到落点（画布 updateData；comic panel.setAsset） */
  commit(task: TTask, targetId: string, assets: GeneratedAsset[]): TCommand[]
  /** 是否把产物攒进计划末尾的聚合（画布现为逐调用落承载节点；comic 不入） */
  shouldCollect(task: TTask, assets: GeneratedAsset[]): boolean
  /** RunRecord 留痕命令；返回 null 保留为「能力可选」的表达（两个工作台目前都落留痕） */
  record(task: TTask, record: RunRecord): TCommand | null
  /** 计划收尾：聚合产物落成工作台自己的形态（画布：承载节点 + 素材） */
  finalize(plan: RunPlan<TTask>, collected: CollectedAsset[]): TCommand[]
}
```

**`record` 两侧的差异（M6-15 之后，一个特别能说明「适配器吸收存储形态差异」的例子）**：

| | canvas（`CanvasPlacement`） | comic（`ComicPlacement`） |
| --- | --- | --- |
| 返回命令 | `node.runRecord.append` → 落 **`runRecords` 表** | `panel.runRecord.append` → 追加到**格内 `runs` 数组** |
| 为什么不同 | 画布是「图 + 补丁流」双存储，图快照与留痕必须分表 | comic 是单聚合对象、单写通道（整对象落一行），留痕天然属于聚合体 |
| 版本号从哪来 | 由调用方（引擎侧记录 + store）给 | **由 reducer 从该格历史推出**（`appendPanelRun`），载荷类型 `PanelRunInput` 刻意不含 `version` |

同一句 `RunRecord` 进、两种存储形态出——全程**引擎不认识任何一种**。这正是 §5.5 路径 B 想兑现的那件事。

逐个 task：freeze RunSnapshot → 调用 writeBack 创建承载节点占位 → 发请求。失败：网络中断 / 408 / 429 / 5xx 重试，退避 1s、2s + 抖动，遵守 Retry-After。取消：runPlan-level AbortSignal 触发时，已成功的 RunTask 保留结果写回（不撤销）、未启动的跳过、正在跑的终止（runEngine 自身不再写回任何内容，调用方在 finally 块中根据 RunSummary 决定补发 `stale.clear`）。

结果落位是 `domain/layout/resultGroupLayout` 的纯函数输出，执行器只负责按坐标通过 writeBack 提交 Command。

```ts
// features/canvas/execution/useExecution.ts（绑定）——【M6-1 更正】同 runEngine，原设计在 features/shared/，实为画布专用，已归位
//
// 职责划分（这是 useExecution 与 runEngine 的唯一分工方式）：
//   useExecution 是宿主——持有全部可变状态与生命周期：
//     · 创建 AbortController（每次 startRun 一个，与 plan 同生命周期）
//     · 创建 writeBack 闭包（把 dispatch 包进去，runEngine 传来的 transaction 原样透传）
//     · 持有 taskStates / runningPlanId，响应 onTaskUpdate 驱动 React 重渲染
//     · 取消时调 controller.abort()，并在结束后清理 taskStates 与 runningPlanId
//     · runEngine resolve 后：落 RunRecord（summary.records）、补发 stale.clear
//   runEngine 是纯执行器——不持有状态、不认识 React、不知道 dispatch 是什么：
//     · 只按 plan 调度、重试、调用 writeBack 与 onTaskUpdate
//     · 可被直接单测：喂一个 mock writeBack 与 mock channelResolver 即可跑完整条计划
export function useExecution(): {
  startRun(plan: RunPlan): Promise<RunSummary>
  cancelRun(runPlanId: string): void
  runningPlanId: string | null
  taskStates: Map<string, RunTaskState>
  isRunning: boolean
}
```

### 5.8 扩展位二：UI 打磨 · ✅ 已实现

打磨是高频、低风险、高重复的改动，架构为此提供三件东西：

**① 令牌单点**

| 内容 | 位置 | 说明 |
| --- | --- | --- |

**③ 组件陈列室**

- 配合 Playwright 截图，视觉回归只需对这一页批量截图，不必先操作到某个业务状态

打磨流程由此变成：改组件 → 看陈列室 → 比对截图 → 提交。
