## 2. 分层与依赖方向

### 2.1 分层图 · ✅ 已实现

```
┌──────────────────────────────────────────────────────────────┐
│  app          应用外壳：路由、启动、平台注入、错误边界          │
├──────────────────────────────────────────────────────────────┤
│  pages        页面装配：HomePage / CanvasPage / SettingsPage   │
├──────────────────────────────────────────────────────────────┤
│  workbenches   工作台层（可并列多个，互不引用）                  │
│  canvas/ 画布工作台   │  （后续）comic/ 漫画剧工作台 …          │
│  surface/layer/frame/nodes    │  panels  creation-panel/pickers  │
├───────────────────────┴──────────────────────────────────────────┤
│  features     交互控制器：共享（视口/选择/剪贴板/执行）          │
│               工作台专有控制器随各自工作台目录存放                │
├──────────────────────────────────────────────────────────────────┤
│  state        共享切片（project/task/channel/asset/ui）           │
│               工作台切片按工作台注入，随工作台生命周期创建销毁     │
├──────────────────────────────────────────────────────────────────┤
│  domain       领域层（纯 TS，无 React、无 IO）                    │
│  shared/ 跨工作台内核（素材/任务/能力）｜ 工作台私有领域          │
├──────────────────────────────────────────────────────────────────┤
│  platform     平台端口与实现：storage / network / creds / files   │
├──────────────────────────────────────────────────────────────────┤
│  ui           无业务展示组件：Button / Menu / Chip / Lightbox     │
└──────────────────────────────────────────────────────────────────┘
```

工作台层是并列关系而非包含关系：画布是一个工作台，漫画剧是另一个。它们共享 `features` 的通用控制器、`state` 的共享切片、`domain/shared` 与以下全部基础设施，彼此之间不产生引用。

### 2.2 依赖方向表 · ✅ 已实现

| 层 | 可依赖 | 可被依赖 |
| --- | --- | --- |
| `app` | 全部 | — |
| `pages` | `workbenches` `features` `state` `ui` | `app` |
| `workbenches/*` | 本工作台目录内 `features` `state` `domain` `platform` `ui` | `pages` |
| `features` | `state` `domain` `platform` | `workbenches` `pages` |
| `state` | `domain` `platform` | `features` `workbenches` `pages` |
| `domain` | `domain` | 全部上层 |
| `platform` | `domain` 的类型 | `state` `features` |
| `ui` | `ui` | 全部上层 |

依赖只能从上层指向下层，且**同级工作台之间无横向依赖**。`domain` 不 import React、不 import platform、不读写全局状态；`ui` 不 import `state`；`workbenches/canvas` 与 `workbenches/comic` 互不 import。这三条是硬约束，由 §7 的工具链强制。

**应用壳额外约束**（2026-09-27 新增）：

- `app/AppShell` 不得 import `workbenches/*` 或 `pages/*` 的内部实现；
- 壳中的「所有项目」树只读 `projects` / `projectFolders` 仓储与会话态，不读取画布 store；
- 画布内日志 / 缩放 / 工具条不进应用壳，避免壳与工作台耦合；
- 侧栏状态只存在 `app/sidebarState` 的**模块级订阅值**，不落库、不进命令层。
  它有两个来源、一个派生宽度：**常驻 `pinned`**（用户按折叠按钮锁定，**落 `localStorage`**、
  跨重启记住）与**悬停 `hovering`**（临时、不落盘）；`open = pinned || hovering`
  （用户 2026-10-06 改的口径，取代旧的"不落盘 + 刷新回收起"）。

### 2.3 为什么这样切 · ✅ 已实现

| 判断 | 结论 |
| --- | --- |
| 节点视图里能不能直接改 store | 不能。视图通过 `emit(event)` 向上请求，由页面装配层转成命令 |
| 交互逻辑放在节点组件里还是独立 hook | 独立 hook。`features/` 下的控制器可被画布、小地图复用 |
| 布局算法放哪 | `domain/layout`。它是纯函数，输入节点框与数量，输出坐标，可以脱离浏览器测试 |
| 网络请求放哪 | `platform/network`。业务代码只接触 `ChannelAdapter` 接口 |
| 通用组件放哪 | `ui/`。判断标准是「不拥有业务状态」 |
