## ⛔ 整个画布黑屏 · 节点视图读了缺失字段（2026-09-23）

**用户报**：「我的项目黑屏了」。

**排查**（重启开发服务后，Vite 日志露出被旧进程缓存挡住的那条真实报错）：

```
[Unhandled error] TypeError: Cannot read properties of undefined (reading 'length')
 > PromptNodeView.tsx:205
     {data.text.length} 字
```

**根因**：`PromptNodeView` 里**同一份数据、两处口径不一致**——
上面渲染正文时写了 `data.text ? … : …`（防了空值），
下面统计字数却直接读 `data.text.length`（没防）。
只要 `text` 是 undefined（老库数据、或某条创建路径漏带该字段），这一行就抛异常，
而 **React 的渲染错误会把整棵树带下去** ⇒ 用户看到的是**整个画布黑屏**，
不只是「这个节点显示不出来」。代价还包括未保存的操作全部丢失。

**修法**：`(data.text ?? '').length`；顺带把同文件工具按钮的禁用判定
（`data.text.length === 0`）与循环节点的 `data.prompts` 多处读取一并加固。
循环节点收成一个 `const prompts = data.prompts ?? []`，让「缺字段」只在一处处理。

**这一类缺陷的通则**：视图层读节点数据时**一律按可选处理**。
节点数据来自持久化，会经历版本升级、老库数据、别的创建路径，
「类型上必填」只保证新写入的数据，不保证读到的数据。
**崩一次的代价（整页白屏 + 丢用户操作）远大于多写一个 `?? ''`。**

**为什么之前没被发现**：热更新时页面状态错乱，报错被旧进程的日志缓存挡着；
重启服务后才露出。这也是「先重启再判断」这条排查顺序的价值。

**验证**：新增 `PromptNodeView.crash.test.ts`（6 项，覆盖 text 为
undefined / null / 空串 / 有内容 / 整个 data 为空对象）。
**故障注入**：把修复改回 `data.text.length`，4 项立刻变红、报的正是黑屏那条错误。
全量 1268 项 + 冒烟 919/919。

## 配方记忆（§6.8）口径修订 · 2026-09-23

| 项 | 原口径 | 新口径（用户拍板） |
| --- | --- | --- |
| **记录时机** | 生成**成功**那一刻才记 | **改了参数就记**——不等生成 |
| **新建节点来源** | 解析链：节点自身 → 该渠道记录 → 第一个渠道首模型 | 同上，但「该渠道记录」现在由**每次参数变更 + 每次新建**持续写入 |
| **新建节点本身是否入库** | 不入库（只是显示） | **入**：新建时把落进节点的那套值也记一遍，链才闭合 |

**为什么改**：用户原话「只要我改了参数，他也给我记住……后面每次新建的节点参数就来自于上个新建节点时候的参数」。
原口径要求「必须先成功生成一次」才会记住，与用户直觉不符——他改完参数就期望下次继承。

**落点**：
- `domain/project/generationPreset.ts` → `RECIPE_TRACKED_KEYS` / `isRecipeEdit`（哪些改动算改配方，唯一判据）
- `workbenches/canvas/panels/PanelLayer.tsx` → 参数类事件里就地 `rememberRecipe`
- `pages/CanvasPage/CanvasPage.tsx` → 新建节点时把落进节点的值也记一遍
- `workbenches/canvas/execution/CanvasExecutionProvider.tsx` → **移除**「生成成功才记」那段（有意去掉，注释说明防止被加回来）

**验证**：`generationPreset.test.ts`（24 项，含「内容类改动不算配方」）+ `channelStore.recipe.test.ts`（10 项，
含「配方落库 → 新会话读回」「同会话先建后改再建」「记录模型下架后回落」）+ 全量 1241 项 + 冒烟 899/899。

### ⚠️ 第一版没生效 · 真机复现后修掉（同日）

用户实测报「**改了参数，再新建还是原本的默认**」——上一版只过了单测，真机没通。

**真机复现**（`scripts/probe-recipe-live.mjs`，注入一个启用渠道后按用户路径走）：
改比例 → 节点 data 变了（`ratio: "1:2"`）→ 但 **`presets` 表一条都没有**。

**两个断点，都在「从哪取值」这一层**：

1. **记录时从节点 data 取渠道 / 模型** —— 而节点为空、只有面板兜底显示着它们时，
   取到的永远是空 ⇒ 守卫 `if (!channelId || !model) return` 把每一次记录都挡掉。
   **修法**：改由**面板把当前显示的整套值带过来**（`PanelEvent.recipe?: RecipeSnapshot`），
   面板才是唯一知道「用户眼前这套是什么」的地方（它有解析链算出的 `shownChannelId` / `shownModel`）。
2. **只在上一次修里写了「新建时记」，但改参数那条仍要求节点自带模型** —— 同一个根因的两面。

**教训（写下来防再犯）**：新增的 `recipe` 字段是**事件自带的快照**，
宿主层不再自己从 store 里凑值。这是本项目第 N 次栽在「两处各自取一份值」上——
**同一个事实只允许一个来源**；跨层传递时，谁手上最准就由谁带出来。

**验证（这次是真机）**：冒烟新增 **G68**（8 项），按用户路径真点：
新建 → 改比例（**不生成**）→ 再新建，断言**落库的 presets 与新节点 data**（不看面板显示值
——那正是当初骗过我们的东西）。**故障注入**：把 `event.recipe` 改成 `undefined`，
G68 的两条核心断言立刻红（`配方参数 ratio=null`、`B=null`），证明断言真的在测东西。
全量 1242 项 + 冒烟 907/907。

### ⚠️ 第二版仍没生效 · 多渠道串味（同日，用户再报）

用户复测仍报「没有带上」，但补了一条**决定性线索**：

> 「直接按住 Alt 拖动复制后的节点是带上的。」

复制能带上 ⇒ 节点 data 与配方**本身都是对的** ⇒ 问题只在**新建那条取值路径**。

**真因**：解析链第 2 档写的是「按**渠道列表顺序**取第一条记过的配方」。
多渠道时必然出错——用户在渠道乙上改的参数，会被排在列表前面的渠道甲那份记录盖过。
**渠道顺序与「用户最近改的是哪条」根本没有关系**，拿它当判据是错的。

**修法**：改成按 `savedAt` **倒序**取最近改过的那条。顺带处理一个隐患：
`Date.now()` 只有毫秒精度，两次快速改动可能并列 ⇒ 排序结果不确定
（表现仍是「刚改过却取了另一条」）。`channelStore` 里加单调递增水位 `nextRecipeAt()`，
保证每次记录的 `savedAt` 严格大于上一次；从库里读回时也把水位抬起来。

**验证**：单测 `channelStore.recipe.test.ts` 新增两条（多渠道取最近 + 同毫秒）。
冒烟新增 **G69**（7 项）：真建两条渠道 → 在**第二条**上改参数 → 新建 → 断言继承第二条那套。
**故障注入**：去掉按时间排序（改回 `[...channels]`），那两条单测立刻红，证明断言有效。
全量 1244 项 + 冒烟 914/914。

### ⚠️ 第三版：真正的根因是**三个新建入口不一致**（同日）

用户仍报「新建节点后保存参数，再新建还是不行」，并让我参考「大雄无限画布」的做法。
查下来根因分两层：

**① 入口不一致（主因）**：新建生成节点有**三个入口**，只有左栏「＋」菜单带了默认配方：

| 入口 | 改前 | 改后 |
| --- | --- | --- |
| 左栏「＋」菜单 | 带默认配方 | ✅ 走统一入口 |
| 画布空白**右键**菜单 | 裸 `node.create`，data 为空 | ✅ 走统一入口 |
| 拖线到空白「新建并连接」 | 同上 | ✅ 走统一入口 |

从后两个入口建出来的节点没有渠道 / 模型，用户在它上面改参数时，配方守卫
（要求渠道 + 模型齐全）一条都记不上 ⇒ 表现正是「改了参数没带上」。
**修法**：抽 `features/canvas/createNodeWithDefaults.ts`，拆成
`resolveDefaults()`（异步，事务外）+ `applyDefaults()`（同步，可放进事务）。
拆两段是因为拖线新建要求「建节点 + 连线 = 一次撤销」，而 `beginPlan`/`endPlan`
之间不能有 await（会让出事务边界，撤销断成两步）。

**② 顺带踩的坑（已修并加断言）**：`node.create` 的 data 是**整体替换** spec 默认值，
不是合并。给所有类型无条件注入 `{channelId, model}` 会把气泡节点自己的默认结构挤掉。
已改成**白名单**（只有 generation / batch / prompt 注入）。

> 另一条独立教训：单测里 `getSpec()` 返回 null（**没 import `registerAllSpecs`**）——
> 于是 `newGeneratingNodeData` 拿不到 spec 默认数据，生成节点丢掉 `mode` 等字段，
> 而测试却在「空跑」。真机由应用启动时注册，单测必须自己来。**这一步漏了会得到假绿**。

**验证**：单测新增 `createNodeWithDefaults.test.ts`（含分组不得被注入）；
冒烟新增 **G70**（4 项：三个入口各建一次，逐个断言都带默认渠道与模型）。
全量 1249 项 + 冒烟 918/918。

## 技能库（Skill）· 2026-09-24

用户要「在提示词节点的创作面板加系统提示词 / skill 功能，这样我可以用 skill
写出自己的详情页策划」，并要求「能做 skill 库、上传 md 自动解析、支持长文本框」。
第一版按 **A 方案**做（正文只当系统指令，不做变量替换）——用户确认。

**定位**：技能不是新机制，是既有链路的**参数化**。提示词节点上的
「优化 / 翻译 / 反推」走的都是同一条：

```
系统指令 + 节点正文 → 文本模型 → 结果写回
```

三者唯一的差别就是那段系统指令（`promptTools.PROMPT_TOOL_SYSTEM` 里的三个常量）。
技能把这段指令**从写死改成用户可管理**，执行链路零改造（复用 `completeText`）。

### 做了什么

| 项 | 落点 |
| --- | --- |
| 领域模型 + md 解析 + 校验 | `domain/prompt/skill.ts`（16 项单测） |
| 存储 | `state/project/skillStore.ts`：内置进 `builtinSkills`，用户技能进 `skills`；旧 `presets:skill:*` 自动迁移 |
| 应用级 Provider（带变更订阅） | `app/providers/SkillStoreProvider.tsx` |
| 面板上的技能选择器 | `panels/SkillPicker.tsx` |
| 技能库页面（卡片浏览 → 编辑；含内置 / 我的 / 功能预设词） | `pages/SkillsPage/*`，路由 `/skills` |
| 执行接入 | `usePromptTools.runSkill`（与 `run` 共用 `invoke`） |
| 长文本输出 | 结果 ≥200 字时自动打开大编辑框（复用 `TextEditorLayer`） |

### 几个刻意的决定

- **2026-10-01 改为内置 / 用户分表**：第一版为省一次 Dexie 迁移复用了 `presets`，
  但内置技能需要稳定只读来源，不能与用户可编辑内容同表；现按产品文档 §7A.3 正式拆成
  `builtinSkills` 与 `skills` 两张表。旧 `skill:` 行会自动迁移，用户内容不丢。
- **技能库独立成页**，不塞进设置页：设置页已在管渠道 / 协议 / 模型三件事，
  而技能是**内容**（写正文、导入 md、逐条编辑），与「配置连接」是两类工作。
- **md 两种格式都收**：有 frontmatter 读 frontmatter（与 Codex 的 SKILL.md 同构，
  别处的 skill 能直接导入）；没有就**整份当正文、文件名当名称**（随手写的也能导）。
- **逐个文件独立成败**：一次导入多个时，其中一个格式不对不该让其余也失败 ——
  收集成功数与失败原因一起报。
- **面板缺技能时给可点出口**，不只是写「去后台添加」：只给文字让用户自己找路，
  是本项目吃过亏的一类反馈缺陷。

## 循环节点：落位源改成下游生成节点 + 槽位按轮次铺开（2026-09-24）

用户报三件事，其实是**一条链**上的三个表现：

> 「次数是 2、并发的，下游链接了生成节点后，点击循环节点的生成按钮应该是在下游的
>  生成节点右边出现两个槽位去生成。目前我并发是先把下游的生成节点变成生成状态后，
>  生成完毕后再从循环节点新建了一个槽位出来 —— 槽位应该出现在下游生成节点的右边，
>  线条应该是链接下游生成节点的，不是从循环节点出来的，因为参数是靠下游生成节点控制的」

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 槽位挂在**循环节点**右边 | 计划用 `originNodeId = 循环节点` 发起，落位源自然是它 | 改成对**每个下游生成节点**各发起一次（`originNodeId = 该节点`） |
| 2 | 线条从**循环节点**画出 | 同上（`slot.connectFrom` 是循环节点） | 同上；连线的含义本就该是「这个产物来自这次生成」 |
| 3 | 跑完一轮才冒出一个槽位 | 逐轮各建一个计划，每轮 `slotIndex` 都从 0 起算 ⇒ 两个承载节点算到**同一格位**、重叠；而 `single` 模式下第一轮还会占用下游节点本身 | ① 用 `single-alt`（一律铺新承载节点，不占下游节点）；② **把 N 轮的任务合并成一个计划**，槽位按 `slotIndex / slotCount` 统一重排 |

**第 3 点是关键**：只改①②不够。「逐轮各建计划」时每轮的槽位索引都是 0，
两个节点会重叠在同一位置 —— 数量对了，但用户看到的是「只有一个」。
合并成一个计划后，引擎按总数统一铺开，才是「并排两个槽位」。

**实测几何**（真机）：

```
生成节点 right=1100
承载槽位 left = 1188, 1444   ← 都在生成节点右侧，且 x 递增不重叠
```

**验证**：冒烟 G67 扩到 **26 项**，新增两条几何断言 ——
「两个承载槽位都在下游生成节点右侧」「两个槽位并列排开、互不重叠」。
只断言「节点数 +2」是不够的：那正是上一版的状态（两个槽位叠在一起、数量对但看不见两个）。
全量 1285 项单测 + 929 项冒烟。

### ③ 变量芯片（`workbenches/canvas/text/TokenEditor.tsx`）

用户要的是「输入框内 `[计数]` 自动变成带 × 的按钮」——这是**富文本**语义，

### ② 批量输入卡顿

根因：面板 `onChange` 每敲一键就 `dispatch` 一次 `node.updateData`，

## ⛔ 缩放就黑屏：ResizeObserver 用了屏幕矩形（2026-09-24）

**用户报**：「我缩放他就黑屏了，从这个角度查一查，上次都修过一次了，这次又出现了」。

**根因**（上一轮我引入的）：循环节点「高度跟随内容」用了 `getBoundingClientRect().height`
去写世界坐标的 `node.h`。而**画布缩放是 `[data-world]` 上的 CSS `scale(zoom)`** ——
那个 API 返回的是**变换后**的屏幕像素，与世界坐标**不同量纲**。

后果是一个反馈环：

```
写高度 → 内容重排 → ResizeObserver 触发
      → 又量到缩放后的值 → 再写一个错误的世界高度 → …
```

缩放过程中这个环会高速空转，页面崩溃。

**修法（三处一起改）**：

1. **量布局高度而非屏幕矩形**：改用 `offsetHeight` —— 它是布局尺寸，**不受 transform 影响**，
   与世界坐标同量纲。
2. **依赖改为空、读取走 ref**：`node.h / node.w / emit` 全部放进 ref。
   若进依赖，每次写回高度都会让 effect 重建 + 重新 observe，缩放时形成重建风暴。
3. **容差 4 → 8px**：`offsetHeight` 是取整值，容差太小会在临界点反复触发。

**实测证据**（zoom=0.826 时）：

```
offsetHeight                 = 318   ← 恒定，不随缩放变
getBoundingClientRect().height = 262   ← 跟着 zoom 变小（318 × 0.826）
```

即：用 offsetHeight 时**缩放根本不会唤醒 observer**，环从源头断掉。

⚠️ **未能完整复现**：探针里连续缩放（1.0 / 1.197 / 5.0 / 0.826）页面均未崩溃、零报错，
估计需要特定缩放幅度或更快的连续操作才触发。故本条修的是**确证的隐患**，
而非「确认修好了那个黑屏」。若缩放仍黑屏，需按 F12 抓当时报错再定位。

**验证**：tsc / eslint / depcruise 全绿；单测 1285 项；冒烟 927/927。

## 高度自适应：从「查表」改成「量出来」（第三次修，2026-09-24）

这个 bug 前后修了三版，前两版都是**查表**：按「哪些通道开着」取一个高度常数写回节点。
查表法的致命弱点是**常数会过期** ——

- 第一版常数按「批次在底栏」算；批次挪回图片面板后就不对了；
- 第二版常数按「底栏横排」算；底栏改竖排后又不短了。

两版都以「内容被裁」收场。第三版彻底不用常数：给内容包一层 `data-loop-content`，
用 `ResizeObserver` 量它的**实际高度**写回节点（`+ 18` 边框与内距）。
**布局再怎么改，量出来的永远是真实值**——没有常数，也就没有过期。

并且改成**双向跟随**（放大与缩小都做）：只放大不缩小的话，关掉通道后底部留一大块空白，
而「完全自适应」正是用户的原话。容差取 4px，避免亚像素在临界点反复抖动。

> 这条与「用户手动拉高节点」有冲突：双向跟随会把手动拉高也压回内容高。
> 这是**有意的取舍** —— 循环节点是参数卡，高度跟内容走才对；
> 要留白随时可以再拉。反之若只收不放，另一个方向立刻违背「自适应」。

**验证**：真机探针量三条（footer 在节点内、图片面板在节点内、批次与面板同宽）
＋ 关提示词后节点高度从 336 收到 213 且 footer 仍在节点内。

## 循环节点「一键运行」接通执行（§6.22）· 2026-09-23

用户要求：「这个循环节点下方链接好生成节点的时候他就可以一键运行了，走的就是生成节点的参数」。
此前按钮是**如实禁用**的（执行未接），本轮接通。

**实现方式**：不做成「把 N 轮塞进同一个 RunPlan」。那需要改 `buildRunPlan` 的主流程
（为每轮复制一份下游 task、各带该轮输入），而它是画布与其后工作台共用的形状，
为单个节点类型改主流程风险过大。改成**逐轮构建并执行**：

| 步骤 | 做法 |
| --- | --- |
| 展开轮次 | `planLoopRounds`（纯函数）：图片按轮次**切片**、提示词按轮次**取模轮换**并替换变量 |
| 传递输入 | 每轮把该轮的提示词与素材写进**循环节点自己**的 `__roundPrompt` / `__roundAssets` |
| 下游取用 | `generation.collectInputs` 新增 loop 分支，读这两个字段（下游零改造） |
| 执行 | 用该轮输入 `buildRunPlan('single')` → `launch`，一轮 await 完再下一轮 |

**为什么不改写下游节点的 `prompt`**：那需要备份 + 恢复，异常路径漏一次就是**数据损坏**；
而「提示词是循环分发出来的输入」语义上也该走 `inputs`，不是改下游自己的字段。

**顺带修掉的一个假判据**：`hasRunnableDownstream` 起初用的是 `canBuildRequest`，
而它只问「节点类型是否可生成」，**不看渠道 / 模型配没配** ⇒ 按钮亮着、点下去空跑。
改成与 `emptyPlanReason` 同口径（渠道 + 模型齐备）。这是「同一个事实只允许一个来源」
那条通则的又一次印证：NodeLayer 里原本抄了一份判断，已改为复用同一个函数。

**已知限制（如实记下）**：`mode: parallel` 目前仍**串行执行**。
并发要处理「多轮同时改同一批下游节点」的写入竞态，风险大于收益，
先保证能跑且结果正确；设计文档里 `parallel` 也注明「受并发上限约束」。

**验证**：
- 单测 `loopRun.test.ts` **17 项**：逐轮切片（含最后一轮不足 batch）、起始越界、
  提示词取模回绕、三个变量替换（含全角写法）、上游收集、可运行判据（含「只配渠道没选模型」）。
- 冒烟 G67 扩到 **24 项**，新增端到端：设次数 2 → 点一键运行 → 断言**有图节点 0 → 2**。
  判据用图数而非节点总数：第一轮产物会落进已有空下游节点（`slot: reuse`），总数只 +1。
