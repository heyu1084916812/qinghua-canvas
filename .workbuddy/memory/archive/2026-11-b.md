## 2026-11-14 循环节点参数浮层被遮住（#1100）

- **`content-visibility: auto` 的 paint containment 是常驻的**，不是「只在视口外才生效」。2026-11-08 性能提交 `872543e2` 给 `.react-flow__node` 加上它之后，任何**画出节点框**的后代（循环节点数字浮层：宽 172 / 控件 67，天生左溢 40px）都被裁到框内，而且**被裁掉的部分连 `elementFromPoint` 都拿不到** ⇒ 表现为「面板被遮住 + 那几格点了没反应」。`.body { overflow: visible }` 再怎么放开也没用：裁它的不是 `.body`，是更高一层的节点包装。
- 修法：给 `:has([data-loop-node])` 单独 `content-visibility: visible`（240 宽小参数卡，不属于 #1021 的性能压力面）。A/B 实测：只改这一条，8 个档位全部恢复可点。
- 浮层还有两个「越界会撞墙」的方向，一并收进 `src/ui/popoverPlacement.ts`（纯函数 + 11 条单测）：越过节点**上沿**会落进 `FlowNodeHeaderLayer`（z-index 12，整层在节点层之上 —— 节点在一个 `transform` 视口层里，永远压不过它）⇒ 标题画在浮层上还吞点击；越过**画布视口**左右缘会被 `.surface{overflow:hidden}` 裁掉。规则：装不下就朝下弹（下方是空白画布）、横向用 `margin-left` 收进视口（`transform` 留给居中/入场动画）、两头都装不下就保持朝上不乱翻。
- 探针口径：判据必须用 `elementFromPoint(元素中心) === 元素`（命中测试），不要用「DOM 里有没有这个节点」—— 被 paint containment 裁掉的元素**仍在 DOM 里**，计数断言全绿而用户点不到。

## 2026-11-14 RunningHub 工作流 / 三来源渠道调研（#1104–#1107）

- **RunningHub 只有三条接口路线**，判断"接了没有"必须分清：① 标准模型 `POST /openapi/v2/{endpoint}`（扣**金额**，轻画已接）；② AI 应用 `GET /api/webapp/apiCallDemo` + `POST /task/openapi/ai-app/run`（扣**RH 币**，轻画已接但参数写死）；③ **自建工作流** `POST /api/openapi/getJsonApiFormat`（拿整份工作流 JSON）+ `POST /task/openapi/create`（提交，扣**金额**）—— **轻画完全没有**（全仓搜不到 `task/openapi/create`）。别再凭"渠道里有 runninghub"就以为工作流也接了。
- **参数"暴露/隐藏"是两层，不是一层**：AI 应用的开放字段是**作者在 RunningHub 网页端勾的**（`apiCallDemo` 只回开放过的，别的一律拿不到）；自建工作流**没有暴露机制**，`getJsonApiFormat` 把每个节点 `inputs` 全给你 ⇒ 必须自己「拉全量 → 默认全隐藏 → 用户勾选」。参考项目 `Infinite-Canvas/main.py` 的 `runninghub_collect_workflow_fields()` 里 `enabled: False` 就是写死的默认值，这条口径可直接抄。
- **媒体字段两条路不能混**（以前踩过 #691 的同类坑）：工作流 / AI 应用的 IMAGE·VIDEO·AUDIO 字段吃的是 `POST /task/openapi/upload` 回来的 **`fileName`**，不是 URL、不是 data URI；端点路才是内联。
- **字段模型**（抄 `runninghub_normalize_field`）：`{id:"<nodeId>::<fieldName>", nodeId, fieldName, fieldValue, fieldType, label, enabled, group, note, options[], min, max, step, random_enabled, imageOrder, required}`；`fieldType` 见过 TEXT/NUMBER/BOOLEAN/IMAGE/VIDEO/AUDIO，`options[]` 非空就是下拉。
- **不许按猜的字段写死类型**：`apiCallDemo` 是否返回 `description` / `nodeName` 两份官方实现都没用到（只有参考项目读了 `label`/`title`）⇒ 先抓一份真实响应当夹具再定类型。同理 `nodeInfoList.fieldValue` 该传字符串还是原类型（参考项目全转字符串、官方插件传原值）也必须真跑一次。
- **架构结论（别新建节点类型）**：把来源做成生成节点上的一行选择（`data.source`），RunningHub 条目复用现有渠道抽象（`app:<id>` 已在用，新增同构 `workflow:<id>`），于是选路 / 多 Key / 优先级 / 取消 / 错误归一全部继承，`resolveGenerationTarget()` 一行不用改。这与仓库既有口径一致：**能参数化的就别新建机制**。
